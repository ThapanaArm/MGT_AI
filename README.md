# MGT AI Authen — ระบบแชท AI (Claude) พร้อมยืนยันตัวตนและตรวจสอบย้อนหลัง

ระบบให้พนักงานคุยกับ Claude ได้ **หลังล็อกอินเท่านั้น** โดยทุกข้อความถูกบันทึกผูกกับตัวตนของผู้ถาม
ผู้ตรวจสอบค้นย้อนหลังได้ว่า *ใครถามอะไร เมื่อไหร่ จากเครื่องไหน* และมี **เงื่อนไขคัดกรอง** กันข้อมูลละเอียดอ่อน
ไม่ให้หลุดออกไปยังผู้ให้บริการ AI

| ส่วน | เทคโนโลยี |
|---|---|
| Frontend | React 19 + Vite 8 + React Router (JavaScript, ไม่ใช้ UI library) |
| Backend | .NET 8 Web API + EF Core 8 (SQL Server provider) |
| Database | SQL Server 2022 Express — `MGT_AI_Authen` |
| AI | สามผู้ให้บริการ: Anthropic (official C# SDK `Anthropic` 12.45), Google Gemini (REST) และ OpenAI/ChatGPT (Responses API) — โมเดลตั้งต้น `claude-sonnet-5`, เลือกได้ 11 โมเดล |
| เอกสาร | ClosedXML (Excel), DocumentFormat.OpenXml (Word/PowerPoint), PDFsharp (PDF) — MIT ทั้งหมด |
| Auth | JWT (HS256) + refresh token แบบ rotate, รหัสผ่านแฮชด้วย PBKDF2-SHA512 |

## ภาษาของระบบ

- **หน้าจอทั้งหมดเป็นภาษาอังกฤษ** — เมนู, ปุ่ม, label, ข้อความ error, หัวตาราง, หัวคอลัมน์ CSV
  และข้อความใน audit log ทั้งหมด
- **เนื้อหารองรับสองภาษา** — AI ตอบเป็นภาษาเดียวกับที่ผู้ใช้ถาม (ถามไทยได้คำตอบไทย
  ถามอังกฤษได้คำตอบอังกฤษ) กำหนดไว้ใน `Claude.SystemPrompt`
- **การจัดหมวดคำถามและการคัดกรอง policy จับได้ทั้งสองภาษา** —
  `QuestionClassifier` มี pattern ทั้งไทยและอังกฤษ (`ที่ไหน` / `where`, `อย่างไร` / `how` ฯลฯ)
  และ policy rules ตั้งต้นใส่คำทั้งสองภาษาในกฎเดียวกัน เช่น
  `เงินเดือน, ค่าจ้าง, salary, payroll, compensation`
- คอมเมนต์ในโค้ดบางส่วนยังเป็นภาษาไทย (สำหรับผู้พัฒนา) ซึ่งไม่กระทบสิ่งที่ผู้ใช้เห็น

### 1.2 ใส่ API key

แก้ `Backend/MgtAiAuthen.Api/appsettings.Development.json` → `Claude.ApiKey` และ/หรือ
`Gemini.ApiKey` หรือกำหนดเป็น environment variable (แนะนำ เพราะไม่ต้องเก็บ key ลงไฟล์):

```bash
setx ANTHROPIC_API_KEY "sk-ant-..."
```

```bash
setx GEMINI_API_KEY "AIza..."
```

**ใส่เจ้าใดเจ้าเดียวก็ใช้งานได้** โมเดลของเจ้าที่ไม่มี key จะขึ้นป้าย "no API key" ในรายการเลือก
และถ้าเลือกจะได้ 503 พร้อมบอกชื่อ setting ที่ต้องตั้ง (ดูข้อ 6.18)

**ไม่ใส่เลยก็เปิดระบบได้** — ล็อกอิน, บันทึก log, คัดกรองคำถาม และหน้าตรวจสอบทั้งหมดทำงานปกติ
เพียงแต่ endpoint แชทจะตอบ HTTP 503 พร้อมข้อความอธิบาย และหน้าแชทจะขึ้นแบนเนอร์เตือน

## 4. ฐานข้อมูล

| ตาราง | เก็บอะไร |
|---|---|
| `Users` | ผู้ใช้, บทบาท, แฮชรหัสผ่าน, ตัวนับล็อกอินผิด, เวลาที่ล็อกบัญชี |
| `RefreshTokens` | เก็บเฉพาะ SHA-256 ของ token ไม่เก็บค่าจริง — มี `RevokedAt`/`RevokedReason` |
| `ChatSessions` | 1 แถว = 1 ห้องสนทนา (ลบ = ซ่อน `IsDeleted` ข้อความยังอยู่) |
| `ChatMessages` | **หัวใจของการตรวจสอบ** — ทุกข้อความถาม/ตอบ + `UserID`, `QuestionType`, ธง policy, token ทุกประเภท, **ค่าใช้จ่าย**, โมเดล, โหมด (Chat/Code), latency, IP, User-Agent |
| `AuditLogs` | เหตุการณ์ระดับระบบ — login/logout, ล็อกอินไม่สำเร็จ, ข้อความที่ถูกระงับ, การเปิดค้น log, การแก้ผู้ใช้/policy/ราคา |
| `PolicyRules` | เงื่อนไขคัดกรอง (Keyword หรือ Regex) + การกระทำ (Block/Warn/Audit) + ระดับความรุนแรง |
| `ModelPricing` | ราคาต่อ 1 ล้าน token ของแต่ละโมเดล + อัตราแลกเปลี่ยน USD→THB + **`Provider`** (Anthropic/Google/OpenAI) |
| `ChatAttachments` | metadata ของไฟล์ที่พนักงานแนบ + SHA-256 (ตัวไฟล์อยู่บน disk) |

จุดออกแบบที่ควรรู้:

- `ChatMessages.UserID` **เก็บซ้ำ** จาก session เพื่อค้น log ตามพนักงานได้เร็วโดยไม่ต้อง join
- `AuditLogs` ไม่มี FK ไปยัง `Users` และเก็บ `Username` เป็นข้อความ — **ลบผู้ใช้แล้ว audit trail ยังอยู่ครบ**
- ทุก timestamp ใช้เวลาท้องถิ่นของเซิร์ฟเวอร์ (`DATETIME2(0)` + `DateTime.Now`) ให้ตรงกับที่ผู้ใช้ในไทยเห็น
- ไม่ใช้ EF migration — DDL อยู่ในไฟล์ SQL ที่ DBA ตรวจได้ก่อนรัน
- **ตาราง `ChatMessages` เลี่ยงทั้ง `PERSISTED` computed column และ filtered index โดยเจตนา** —
  ทั้งสองอย่างทำให้ทุกคำสั่ง INSERT/UPDATE/DELETE บนตารางต้องรันด้วย `QUOTED_IDENTIFIER ON`
  ไม่งั้นได้ error `Msg 1934` ซึ่ง `sqlcmd` ตั้งเป็น OFF โดยปริยาย
  (แอปผ่าน SqlClient ตั้ง ON อยู่แล้วจึงไม่กระทบ แต่ DBA จะแก้ข้อมูลด้วย sqlcmd ไม่ได้
  โดยไม่ทราบสาเหตุ) จึงใช้ computed column แบบไม่ persist และ index ปกติแทน

## 5. เงื่อนไขการค้นหา log

`GET /api/admin/logs/chat` — ทุกพารามิเตอร์เป็น optional และรวมกันแบบ **AND**

| พารามิเตอร์ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `keyword` | ค้นคำในเนื้อหาข้อความ | `keyword=ที่ไหน` |
| `userId` | เจาะจงพนักงานตามรหัส | `userId=2` |
| `user` | ค้นบางส่วนของชื่อผู้ใช้หรือชื่อ-นามสกุล | `user=สมชาย` |
| `department` | แผนก | `department=Sales` |
| `messageRole` | `user` = เฉพาะคำถาม, `assistant` = เฉพาะคำตอบ AI | `messageRole=user` |
| `questionType` | `WHAT` `WHERE` `HOW` `WHY` `WHEN` `WHO` `HOWMUCH` `OTHER` | `questionType=WHERE` |
| `policyFlag` | `Block` `Warn` `Audit` | `policyFlag=Warn` |
| `onlyBlocked` | เฉพาะข้อความที่ถูกระงับ | `onlyBlocked=true` |
| `chatMode` | `Chat` \| `Code` (โหมดที่ใช้ตอนส่งข้อความ) | `chatMode=Code` |
| `sessionId` | ทุกข้อความในบทสนทนาหนึ่ง | `sessionId=<guid>` |
| `from` / `to` | ช่วงวันที่ (`to` ครอบถึง 23:59:59 ของวันนั้นอัตโนมัติ) | `from=2026-09-01&to=2026-09-30` |
| `sortBy` / `sortDir` | `CreatedAt` \| `Username` \| `QuestionType` \| `OutputTokens` \| `LatencyMs` / `asc` \| `desc` | `sortBy=LatencyMs&sortDir=desc` |
| `page` / `pageSize` | แบ่งหน้า (สูงสุด 200 ต่อหน้า) | `page=2&pageSize=50` |

ตัวอย่าง — *สมชายถามคำถามประเภท "อย่างไร" ในเดือนกันยายน 2026 ว่าอะไรบ้าง*:

```
GET /api/admin/logs/chat?user=somchai&questionType=HOW&messageRole=user&from=2026-09-01&to=2026-09-30
```

endpoint พี่น้องที่ใช้เงื่อนไขชุดเดียวกัน:

- `GET /api/admin/logs/chat/stats` — สรุปยอด, แยกตามประเภทคำถาม, พนักงานที่ถามมากสุด, รายวัน
- `GET /api/admin/logs/chat/export` — CSV (UTF-8 **with BOM** เปิดใน Excel ภาษาไทยไม่เพี้ยน, สูงสุด 20,000 แถว)
- `GET /api/admin/logs/audit` — ค้น audit log (`keyword`, `userId`, `user`, `category`, `action`, `onlyFailed`, `from`, `to`)
- `GET /api/admin/logs/filters` — ค่าเติม dropdown ตัวกรองบนหน้าเว็บ

บนหน้าเว็บมีปุ่ม **Common filters** กดครั้งเดียวได้เลย: `"What" questions` / `"Where" questions` /
`"How" questions`, `Blocked only`, `With attachments`, `Code mode`,
`Flagged for monitoring`, `Employee questions only`, `Last 7 days`

### การจัดหมวดคำถามอัตโนมัติ

ทุกข้อความของพนักงานถูกจัดหมวดตอนบันทึก (`QuestionClassifier`) โดยตรวจจากรูปแบบที่เฉพาะเจาะจง
ที่สุดไปกว้างที่สุด เพราะประโยคเดียวอาจเข้าได้หลายหมวด — เช่น "ทำอย่างไร" ต้องได้ `HOW` ไม่ใช่ `WHY`

| หมวด | คำที่ตรวจจับ (ตัวอย่าง) |
|---|---|
| `WHY` | ทำไม, เพราะอะไร, เหตุใด, สาเหตุ, why |
| `HOWMUCH` | เท่าไหร่, เท่าไร, กี่บาท, กี่วัน, how much, how many |
| `HOW` | อย่างไร, ยังไง, วิธี, ขั้นตอน, how to |
| `WHERE` | ที่ไหน, ที่ใด, อยู่ไหน, จากไหน, where |
| `WHEN` | เมื่อไหร่, ตอนไหน, วันไหน, กี่โมง, when |
| `WHO` | ใคร, ผู้ใด, who |
| `WHAT` | คืออะไร, อะไร, หมายถึง, นิยาม, what, which |
| `OTHER` | ไม่เข้าหมวดใด |

## 6. เงื่อนไขคัดกรองคำถาม (Policy)

ก่อนส่งข้อความให้ Claude ระบบตรวจกับ `PolicyRules` ที่เปิดใช้อยู่ (cache 60 วินาที) แล้วเลือกกฎที่รุนแรงสุด:

| การกระทำ | ผลที่เกิด |
|---|---|
| **Block** | **ไม่ส่งให้ AI เลย** — บันทึกข้อความไว้พร้อม `IsBlocked=1`, แจ้งเหตุผลกับผู้ใช้, ลง audit `CHAT_BLOCKED` |
| **Warn** | ส่งให้ AI แต่เตือนผู้ใช้และติดธงไว้ + ลง audit `CHAT_FLAGGED` |
| **Audit** | ส่งตามปกติ ติดธงเงียบ ๆ ให้ผู้ตรวจสอบเห็น |

เงื่อนไขตั้งต้น 6 ข้อ:

| ชื่อ | วิธีตรวจ (สองภาษา) | การกระทำ |
|---|---|---|
| Block passwords and system secrets | Regex (`password:`, `api_key`, `sk-ant-`, `รหัสผ่าน:`) | Block / High |
| Block Thai national ID numbers (13 digits) | Regex | Block / High |
| Block credit card numbers | Regex | Block / High |
| Warn on salary and payroll data | Keyword `เงินเดือน, ค่าจ้าง, salary, payroll, compensation` | Warn / Medium |
| Warn on product cost data | Keyword `ต้นทุน, ราคาทุน, cost price, unit cost, margin` | Warn / Medium |
| Audit questions mentioning customers | Keyword `ลูกค้า, customer, client account` | Audit / Low |

> กฎรหัสผ่านตรวจ **การวางรหัสผ่านจริง** (`password: Hunter2`, `รหัสผ่าน: Hunter2`) ไม่ใช่การ
> *เอ่ยถึง* รหัสผ่าน — คำถามอย่าง "How do I reset my password?" หรือ "ลืมรหัสผ่านต้องทำอย่างไร"
> ยังผ่านได้ทั้งสองภาษา ซึ่งเป็นพฤติกรรมที่ต้องการ
>
> ชุดกฎภาษาไทยเดิม (RuleID 1-6) ถูก **ปิดใช้งาน** ไว้ ไม่ได้ลบ เพื่อให้ log เก่าที่อ้างชื่อกฎนั้น
> ยังแสดงชื่อได้ถูกต้อง

### ใส่หลายคำในเงื่อนไขเดียว

`MatchType = Keyword` รับได้หลายคำโดย **คั่นด้วยจุลภาค** (หรือ `|` หรือขึ้นบรรทัดใหม่) —
ข้อความจะเข้าเงื่อนไขเมื่อพบ **คำใดคำหนึ่ง** ไม่ต้องพบทุกคำ เช่นตั้ง Pattern เป็น

```
คืออะไร, ที่ไหน, อย่างไร
```

จะจับได้ทั้งสามคำ หน้าจอแสดง preview ให้เห็นว่าระบบแยกได้กี่คำและคำอะไรบ้าง
หากคำที่ต้องการมีจุลภาคอยู่ข้างในจริง ๆ ให้เปลี่ยนไปใช้ `MatchType = Regex`

Admin แก้ไขได้ที่หน้า **เงื่อนไขคัดกรองคำถาม** และมีช่อง **ทดลองยิงข้อความ**
(`POST /api/admin/policy-rules/test`) ตรวจว่าเงื่อนไขที่เพิ่งตั้งทำงานตามที่คิดหรือไม่
โดยไม่เรียก AI และไม่บันทึกลง log การแชท

ความทนทานที่ใส่ไว้: regex ที่ compile ไม่ผ่านจะถูกข้ามและเขียน error log (ไม่ทำให้ทุกคนแชทไม่ได้),
และ regex ทุกตัวมี match timeout 250 ms กัน catastrophic backtracking

## 6.1 บันทึก Token และค่าใช้จ่าย

ทุกครั้งที่ AI ตอบ ระบบคำนวณค่าใช้จ่ายแล้ว **บันทึกลงแถวของข้อความนั้นทันที** ไม่ได้คำนวณสด
ตอนทำรายงาน — ค่าใช้จ่ายย้อนหลังจึงไม่เปลี่ยนเมื่อมีการปรับราคาหรืออัตราแลกเปลี่ยนภายหลัง
รายงานของเดือนที่ปิดไปแล้วนิ่ง ตรวจสอบย้อนหลังได้

คอลัมน์ที่บันทึกใน `ChatMessages` ต่อหนึ่งข้อความ:

| กลุ่ม | คอลัมน์ |
|---|---|
| จำนวน token | `InputTokens`, `OutputTokens`, `CacheWriteTokens`, `CacheReadTokens`, `TotalTokens` (คำนวณ) |
| ค่าใช้จ่าย | `InputCostUsd`, `OutputCostUsd`, `CacheCostUsd`, `TotalCostUsd`, `TotalCostThb` |
| ที่มาของตัวเลข | `ModelName`, `PricingID`, `UsdToThbRate` — ตรวจย้อนหลังได้ว่าคิดจากราคาชุดไหน เรตเท่าไร |

สูตร: `ค่าใช้จ่าย = (token / 1,000,000) × ราคาต่อ 1M token` แยกคิดทีละประเภท แล้วคูณอัตราแลกเปลี่ยนเป็นบาท
โดย token ที่เกี่ยวกับ prompt cache คิดราคาต่างจาก input ปกติ (เขียน = input × 1.25, อ่าน = input × 0.1)

ราคาตั้งต้นในตาราง `ModelPricing` (USD ต่อ 1 ล้าน token, เรต 36.5 บาท/USD):

| โมเดล | Input | Output | Cache เขียน | Cache อ่าน |
|---|--:|--:|--:|--:|
| `claude-sonnet-5` (ตั้งต้นของระบบ) | 2.00 | 10.00 | 2.50 | 0.20 |
| `claude-opus-5` | 5.00 | 25.00 | 6.25 | 0.50 |
| `claude-opus-4-8` | 5.00 | 25.00 | 6.25 | 0.50 |
| `claude-haiku-4-5` | 1.00 | 5.00 | 1.25 | 0.10 |
| `claude-fable-5-1` | 10.00 | 50.00 | 12.50 | 1.00 |

> ต้องตรวจสอบราคาล่าสุดที่หน้า pricing ของ Anthropic และปรับอัตราแลกเปลี่ยนตามที่ฝ่ายบัญชีใช้
> ก่อนนำตัวเลขไปคิดเงินจริง — Admin แก้ได้ที่หน้า **ราคาโมเดล / อัตราแลกเปลี่ยน**
> ถ้าเจอโมเดลที่ยังไม่มีราคา ระบบจะบันทึก token ไว้แต่คิดค่าใช้จ่ายเป็น 0 และเขียนคำเตือนลง log ของแอป

**หน้ารายงานค่าใช้จ่าย** (`/logs/cost` — Admin และ Auditor) ใช้เงื่อนไขค้นหาชุดเดียวกับหน้าค้น log
แสดงยอดรวมทั้ง USD และบาท, ค่าเฉลี่ยต่อคำตอบ, ยอดสูงสุดต่อคำตอบเดียว
และแยกยอดตาม **พนักงาน / แผนก / โมเดล / วัน** พร้อมสัดส่วนเป็นเปอร์เซ็นต์

ตัวเลขค่าใช้จ่ายยังปรากฏใน 3 ที่: คอลัมน์ในตารางผลค้นหา log, ใต้คำตอบแต่ละข้อความในหน้าแชท
(ให้พนักงานเห็นต้นทุนของคำถามตัวเอง) และในไฟล์ CSV ที่ export

**ข้อความที่ถูก policy ระงับไม่มีค่าใช้จ่าย** เพราะไม่เคยถูกส่งให้ AI — ตรวจได้จาก log ว่าประหยัดไปเท่าไร

## 6.15 ให้ผู้ใช้เลือกโมเดลได้

ในช่องพิมพ์ของหน้าแชทมี dropdown **Model** ให้เลือกโมเดลที่จะตอบ พร้อมแสดงค่าใช้จ่ายโดยประมาณ
ของคำถามหนึ่งข้อ (คิดจาก 700 token เข้า / 600 token ออก) เพื่อให้เห็นผลของการเลือกก่อนกดส่ง

**รายการโมเดลผูกกับตาราง `ModelPricing`** — เลือกได้เฉพาะโมเดลที่ `IsActive = 1` เท่านั้น
ออกแบบไว้แบบนี้เพราะ:

- ทุกโมเดลที่เลือกได้ **มีราคาแน่นอน** ค่าใช้จ่ายจึงถูกบันทึกครบทุกครั้ง ไม่มีช่องที่ใช้งานแล้วคิดเงินเป็น 0
- Admin คุมได้ว่าพนักงานใช้โมเดลไหนได้ **จากหน้าราคาโมเดลที่มีอยู่แล้ว** ไม่ต้องมีหน้าตั้งค่าเพิ่ม —
  ปิด `IsActive` ของโมเดลไหน โมเดลนั้นก็หายจาก dropdown และถูกปฏิเสธถ้ามีคนยิง API มาตรง ๆ
- โมเดลตั้งต้น (`Claude:Model`) เลือกได้เสมอแม้ยังไม่มีราคา (จะขึ้นหมายเหตุว่ายังไม่ได้ตั้งราคา)

**ลำดับการตัดสินว่าจะใช้โมเดลไหน:** ผู้ใช้เลือกมา → โมเดลที่บทสนทนานี้เคยใช้ → ค่าตั้งต้นใน appsettings

จุดที่ตั้งใจทำแบบนี้:

- **บทสนทนาเดิมคงโมเดลเดิม** เปิดแชทเก่ามา dropdown จะเด้งไปเป็นโมเดลที่บทสนทนานั้นใช้จริง
  ไม่ใช่ค่าที่เพิ่งเลือกครั้งก่อน
- **เปลี่ยนโมเดลกลางบทสนทนาได้** (มีข้อความบอกว่า "applies to your next message") เพราะ
  `ChatMessages.ModelName` เก็บเป็นรายข้อความ ไม่ใช่รายบทสนทนา — รายงานค่าใช้จ่ายจึงแยกยอด
  ตามโมเดลได้ถูกต้องแม้บทสนทนาเดียวใช้หลายโมเดล
- **ชื่อโมเดลที่ไม่รู้จักถูกปฏิเสธ ไม่ใช่เงียบ ๆ เปลี่ยนไปใช้ตัวอื่น** — จะได้ไม่มีใครถูกคิดเงิน
  จากโมเดลที่ไม่ได้เลือก ข้อความ error บอกรายการที่เลือกได้ด้วย
- ใต้คำตอบแต่ละข้อความมีป้ายบอกชื่อโมเดลที่ตอบ และ audit log บันทึกโมเดลไว้ทุกครั้ง
  **รวมถึงตอนเรียกไม่สำเร็จ** (เช่นเครดิตหมด) จึงตรวจย้อนหลังได้ว่ายิงไปที่โมเดลไหน

| Endpoint | สิทธิ์ | หน้าที่ |
|---|---|---|
| `GET /api/chat/models` | ล็อกอิน | รายการโมเดลที่เลือกได้ (เรียงจากถูกไปแพง) + ราคาและค่าใช้จ่ายตัวอย่าง |
| `POST /api/chat/messages` | ล็อกอิน | รับฟิลด์ `model` เพิ่ม (ทั้งแบบ JSON และ multipart) |

### สองเรื่องที่การเลือกโมเดลเปิดเผยออกมา (แก้แล้วทั้งคู่)

**1. บางโมเดลไม่รองรับพารามิเตอร์ `effort`** — `claude-haiku-4-5` ตอบ
`400 "This model does not support the effort parameter"` เพราะระบบส่ง `output_config.effort`
ไปทุกครั้ง (ตั้งไว้ `medium`)

แก้แบบ **self-healing** ไม่ต้องมาดูแลรายชื่อโมเดลเอง: เมื่อเจอ 400 ที่บอกว่าไม่รองรับ effort
ระบบจะ **ลองใหม่ทันทีโดยไม่ส่ง effort แล้วจำโมเดลนั้นไว้** ครั้งต่อไปข้ามการส่ง effort เลย
ไม่เสีย round trip ซ้ำ (ดู `ClaudeClient._effortUnsupported`)

**2. API ตอบชื่อโมเดลกลับมาเป็น snapshot ลงวันที่** — ขอ `claude-haiku-4-5` แต่ได้
`claude-haiku-4-5-20251001` กลับมา ชื่อนี้ไม่ตรงกับแถวใน `ModelPricing`
จึง **คิดค่าใช้จ่ายเป็น 0** โดยไม่มีใครรู้ (บั๊กเงียบด้านการเงิน)

แก้ที่ `CostCalculator`: ถ้าหาชื่อตรงตัวไม่เจอ ให้เทียบแบบ **ขึ้นต้นด้วยชื่อที่มีราคา
โดยเลือกชื่อที่ยาวที่สุดที่ตรง** — รองรับ snapshot ของโมเดลใดก็ตามในอนาคตโดยไม่ต้องแก้โค้ดอีก
ส่วน `ChatMessages.ModelName` ยังเก็บชื่อ snapshot เต็มไว้เป็นหลักฐานว่าตัวไหนตอบจริง

ค่าใช้จ่ายจริงที่วัดได้จากคำถามเดียวกัน (`Reply with exactly one word: ok`):

| โมเดล | Token | ค่าใช้จ่ายจริง | เวลา |
|---|--:|--:|--:|
| `claude-haiku-4-5` | 27/3 | 0.0099 บาท | 1,767 ms |
| `claude-sonnet-5` | 327/3 | 0.0256 บาท | 1,236 ms |
| `claude-opus-5` | 327/3 | 0.0639 บาท | 1,465 ms |

ค่าใช้จ่ายตัวอย่างต่อคำถามด้วยราคาตั้งต้นและเรต 36.5 บาท/USD:

| โมเดล | ต่อคำถาม |
|---|--:|
| `claude-haiku-4-5` | 0.14 บาท |
| `claude-sonnet-5` (ตั้งต้น) | 0.27 บาท |
| `claude-opus-5` | 0.68 บาท |
| `claude-fable-5-1` | 1.35 บาท |

## 6.17 โหมด Chat และ Code

เหนือช่องพิมพ์มีปุ่มสลับ **Chat / Code** สองโหมดใช้ system prompt ต่างกัน:

| | Chat | Code |
|---|---|---|
| ใช้ตอน | ถามงานทั่วไป นโยบาย ขั้นตอนทำงาน | เขียนโค้ด แก้บั๊ก รีวิวโค้ด เขียน SQL |
| ความยาวคำตอบ | จำกัด 6 บรรทัด / 5 bullet | ผ่อนให้ยาวได้ เพราะโค้ดที่ถูกตัดใช้งานไม่ได้ |
| รูปแบบ | ข้อความธรรมดา | บังคับใส่โค้ดใน fenced block พร้อม language tag |
| ภาษา | ตอบตามภาษาที่ผู้ใช้พิมพ์ | คำอธิบายตามภาษาผู้ใช้ แต่โค้ด/ตัวแปร/คอมเมนต์เป็นอังกฤษ |

ตั้งค่าข้อความ prompt ได้ที่ `Claude:SystemPrompt` และ `Claude:CodeSystemPrompt` ใน `appsettings.json`
(ถ้า `CodeSystemPrompt` ว่าง ระบบจะถอยไปใช้ `SystemPrompt` — โหมด Code จึงไม่เคยพัง
เพราะลืมตั้งค่า) prompt ของโหมด Code สั่งเพิ่มไว้ 3 ข้อที่ตั้งใจ:

- **ให้โค้ดที่รันได้จริง** ไม่ใช่เศษโค้ดที่มี `...` คั่น และต้องมี import ที่จำเป็น
- **ทักเรื่องบั๊ก / SQL injection / ความเสี่ยงข้อมูลหาย** ในโค้ดที่ผู้ใช้แปะมา แม้ผู้ใช้ถามเรื่องอื่น
- **ห้ามใส่ credential หรือ connection string จริงในตัวอย่าง** เพราะทุกข้อความถูกบันทึกลง log

### การแสดงโค้ดบนหน้าเว็บ

คำตอบที่มี fenced block จะถูกแปลงเป็นบล็อกโค้ดจริง — มีป้ายภาษา, จำนวนบรรทัด,
ปุ่ม **Copy**, และ syntax highlight (highlight.js) บล็อกที่มีโค้ดจะกว้างขึ้นอัตโนมัติ
และเลื่อนแนวนอนได้เองเมื่อบรรทัดยาว

จุดที่ตั้งใจทำแบบนี้: **ไม่ได้เรนเดอร์ Markdown ทั้งก้อน** ตัวเรนเดอร์แค่ตัดข้อความตาม fence
แล้วให้ React แสดงส่วนที่เหลือเป็น text ธรรมดา — คำตอบของโมเดลคือ input ที่ไม่ควรเชื่อ
ถ้าแปลง Markdown เป็น HTML ทั้งก้อนจะต้องมีขั้น sanitise เพิ่ม และพลาดตรงนั้นครั้งเดียว
กลายเป็นช่อง XSS ที่ผู้ใช้เป็นคนป้อนเอง ทางนี้จึงไม่มี HTML จากโมเดลถูกตีความเลย
(`dangerouslySetInnerHTML` ใช้ที่เดียวคือผลลัพธ์จาก highlight.js ซึ่ง escape โค้ดที่รับมาให้แล้ว)
ผลข้างเคียงที่ยอมรับ: `**ตัวหนา**` และ `# หัวข้อ` จะเห็นเป็นเครื่องหมายตามตัวอักษร

### โหมดถูกบันทึกเป็นรายข้อความ

`ChatMessages.ChatMode` (`Chat` \| `Code`) มี CHECK constraint กันค่าอื่น และข้อความ 347 แถว
ที่มีอยู่ก่อนถูก backfill เป็น `Chat`

**ลำดับการตัดสินว่าจะใช้โหมดไหน:** ผู้ใช้เลือกมา → โหมดที่บทสนทนานี้ใช้ล่าสุด → `Chat`

เก็บเป็นรายข้อความ (ไม่ใช่รายบทสนทนา) แบบเดียวกับ `ModelName` เพราะสลับโหมดกลางบทสนทนาได้
— ถามเชิงนโยบายก่อนแล้วขอโค้ดต่อในแชทเดียวกันเป็นเรื่องปกติ — และการเก็บรายข้อความ
ทำให้ผู้ตรวจสอบเห็นได้ว่า **ข้อความไหน** ถูกตอบด้วย prompt ชุดไหน ไม่ใช่เห็นแค่ทั้งบทสนทนา

- ส่งชื่อโหมดที่ไม่รู้จักมา → **400 ไม่ใช่เงียบ ๆ ใช้ค่าตั้งต้น** (เหตุผลเดียวกับชื่อโมเดล)
- เปิดแชทเก่า ปุ่มสลับจะเด้งไปตรงกับโหมดที่บทสนทนานั้นใช้ล่าสุด
- audit log `CHAT_SENT` ขึ้นต้นด้วย `Mode Chat|Code | ...` ทุกครั้ง
- หน้าค้น log มีคอลัมน์ **Mode** (พร้อมชื่อโมเดลใต้ป้าย), ตัวกรอง **Mode**, ปุ่มด่วน `Code mode`
  และคอลัมน์ `Mode` ในไฟล์ CSV
- คัดกรองตาม Policy ทำงานเหมือนกันทั้งสองโหมด — โหมด Code **ไม่ได้** ยกเว้นการตรวจ

| Endpoint | รับเพิ่ม |
|---|---|
| `POST /api/chat/messages` | ฟิลด์ `mode` (`Chat` \| `Code`) ทั้งแบบ JSON และ multipart |
| `GET /api/admin/logs/chat` | พารามิเตอร์ `chatMode` (ค่าที่ไม่รู้จักได้ผลลัพธ์ 0 แถว เหมือนตัวกรองอื่น) |

## 6.18 ผู้ให้บริการ AI รายที่สอง — Google Gemini

ระบบเรียกได้สองเจ้าจากหน้าจอเดียวกัน dropdown เลือกโมเดลจัดกลุ่มตามผู้ให้บริการ
และตาราง `ModelPricing` มีคอลัมน์ `Provider` (`Anthropic` \| `Google`) บอกว่าแถวไหนของใคร

### ต้องทำอะไรก่อนใช้

ใส่ Gemini API key (ขอได้จาก Google AI Studio) ที่ใดที่หนึ่ง:

- `Gemini:ApiKey` ใน `appsettings.Development.json` (ตอนพัฒนา)
- environment variable `GEMINI_API_KEY` (แนะนำสำหรับ production)

**ยังไม่ใส่ก็ใช้ระบบได้ปกติ** โมเดล Gemini จะขึ้นในรายการพร้อมป้าย "no API key"
และถ้าเลือกจะได้ 503 พร้อมบอกชื่อ setting ที่ต้องตั้ง — ระบบ **ไม่** เงียบ ๆ เปลี่ยนไปใช้ Claude แทน
ด้วยเหตุผลเดียวกับการปฏิเสธชื่อโมเดลที่ไม่รู้จัก: ไม่มีใครควรถูกคิดเงินจากบัญชีที่ตัวเองไม่ได้เลือก

ซึ่งเคยเป็นบั๊กในระบบนี้มาแล้ว (ดูข้อ 6.15)

### สิ่งที่ต่างจาก Claude และระบบจัดการให้แล้ว

| เรื่อง | Anthropic | Google | ระบบทำอะไร |
|---|---|---|---|
| นับ token ที่ cache | แยก input กับ cache ให้แล้ว | `promptTokenCount` **รวม** cache มาด้วย | หัก cache ออกก่อนบันทึก ไม่งั้น `TotalTokens` เกินจริงและคิดเงิน cache ในราคา input เต็ม (แพงกว่า 10 เท่า) |
| token ของการคิด | รวมใน output แล้ว | แยกเป็น `thoughtsTokenCount` | บวกเข้า output เพราะ Google คิดเงินในอัตรา output — ถ้าไม่บวกจะบันทึกค่าใช้จ่ายต่ำกว่าบิลจริงทุกครั้งที่โมเดลคิด |
| ค่าเขียน cache | คิด 1.25x ของ input | implicit caching ไม่คิดเงินตอนเขียน | ราคา cache write ของแถว Gemini เป็น 0 และบันทึก cacheWrite = 0 เสมอ |
| พารามิเตอร์คุมการคิด | `effort` | `generationConfig.thinkingConfig.thinkingLevel` | ส่ง `low` ตามค่าตั้ง ถ้าถูกปฏิเสธด้วย 400 จะจำไว้แล้วยิงใหม่โดยไม่ใส่ — วิธีเดียวกับ `effort` ของ Anthropic |
| ไฟล์ข้อความแนบ | มี document block ที่ใส่ชื่อไฟล์ได้ | ไม่มี | ห่อด้วยป้าย `--- Attached file: ชื่อไฟล์ ---` ไม่งั้นแนบหลายไฟล์แล้วโมเดลบอกไม่ได้ว่าเลขมาจากไฟล์ไหน |
| ตอบว่างเพราะ token หมด | ไม่เจอ | โมเดลคิดจนหมดงบแล้วไม่เหลือให้ตอบ ได้ `finishReason: MAX_TOKENS` กับข้อความว่าง | ตอบกลับว่างบประมาณหมดพร้อมบอกให้ถามสั้นลงหรือขยาย `Gemini:MaxTokens` แทนคำว่า "ลองใหม่" ที่ช่วยอะไรไม่ได้ |
| คำตอบถูกตัดกลางทาง | — | `MAX_TOKENS` แต่มีข้อความบางส่วน | ต่อท้ายว่าคำตอบถูกตัด — คำตอบที่ถูกตัดแต่ดูเหมือนจบแย่กว่าคำตอบที่บอกว่าตัด |

### สองเรื่องที่พบตอนต่อ API จริง (แก้แล้วทั้งคู่)

1. **`thinkingLevel` ต้องซ้อนใน `thinkingConfig`** — ส่งไว้ตรง `generationConfig` ถูกปฏิเสธ
   `400 Unknown name "thinkingLevel"` รูปแบบที่ถูกคือ
   `generationConfig.thinkingConfig.thinkingLevel` ตัว self-healing กันไว้ได้อยู่แล้ว
   (ยิงใหม่โดยไม่ใส่) จึงไม่พังตั้งแต่ต้น แต่เสียรอบเชื่อมต่อเปล่าและ**เสียเงินโดยไม่ได้อะไร**:
   วัดจริงบน `gemini-3.8-flash` คำถาม "Say ok" ที่ตอบกลับ 1 token ใช้ thinking ไป **71 token**
   (คิดเงินในอัตรา output = 98% ของบิลข้อความนั้น) พอส่ง `thinkingLevel: low` ถูกที่
   thinking เหลือ **0 token**
2. **`thinkingBudget` ใช้แทนกันไม่ได้** — `gemini-3.5-flash-lite` ปฏิเสธ `thinkingBudget: 0`
   ด้วย 400 แต่รับ `thinkingLevel: low` ปกติ จึงเลือกใช้ `thinkingLevel` ตัวเดียว

### การจัดการข้อผิดพลาด

Error code ที่ API ตอบกลับเป็นกลางทั้งสองเจ้าแล้ว (เดิมขึ้นต้นด้วย `CLAUDE_`):

| code | HTTP | หมายถึง |
|---|---|---|
| `AI_NOT_CONFIGURED` | 503 | ผู้ให้บริการนั้นไม่มี API key |
| `AI_OVERLOADED` | 503 | ปลายทางแน่นหรือ timeout — ส่งใหม่ได้เลย |
| `AI_INVALID_INPUT` | 400 | ข้อมูลที่ส่งไปมีปัญหา (ไฟล์อ่านไม่ได้, ยาวเกิน) |
| `AI_BILLING` | 503 | เครดิต/โควตา/key ผิด — ผู้ใช้แก้เองไม่ได้ |

Gemini ใช้ HTTP status เดียวกันสำหรับเรื่องที่คนละคนต้องแก้ จึงต้องแยกเอง:

- **429** เป็นได้ทั้ง rate limit ต่อนาที (ส่งใหม่แล้วหาย) และโควตารายวัน/ปัญหา billing (ส่งใหม่ไม่ช่วย)
  → ดูในเนื้อ error ว่ามี `PerDay` / `billing` / `free_tier` ไหม แล้วแยกเป็น `AI_BILLING` กับ `AI_OVERLOADED`
- **401/403** คือ key ผิด ถูกเพิกถอน หรือยังไม่เปิด Generative Language API ในโปรเจกต์
  → `AI_BILLING` พร้อมบอกว่าไม่ใช่ปัญหาที่ข้อความหรือไฟล์ของผู้ใช้
- **404** คือแอดมินใส่ชื่อโมเดลที่ Google ไม่มี → ข้อความบอกชื่อโมเดลนั้นตรง ๆ

audit log บันทึกชื่อผู้ให้บริการทุกครั้ง ทั้งตอนสำเร็จ (`Mode ... | model ... | provider ... |`)
และตอนล้มเหลว จึงตรวจย้อนหลังได้ว่ายิงไปที่เจ้าไหน

### จุดที่ตั้งใจออกแบบแบบนี้

- **ผู้ให้บริการตัดสินจากคอลัมน์ `Provider` ไม่ใช่เดาจากชื่อโมเดล** — กฎแบบ "ขึ้นต้นด้วย gemini-"
  จะพาโมเดลที่ตั้งชื่อใหม่ไปผิดเจ้าอย่างเงียบ ๆ ซึ่งหมายถึงเรียกไม่สำเร็จ หรือแย่กว่านั้นคือ
  ไปคิดเงินบัญชีที่ไม่เกี่ยว ฐานข้อมูลมี CHECK constraint กันค่าที่พิมพ์ผิดด้วย
- **`PUT` ที่ไม่ส่ง `provider` มา = ไม่เปลี่ยน** (ไม่ใช่ตกเป็น Anthropic) ไม่งั้น client
  รุ่นก่อนที่ยังไม่รู้จักฟิลด์นี้จะย้ายแถว Gemini ไปเป็น Anthropic โดยไม่มีใครรู้
- **บอกว่าขาด key ตั้งแต่ใน dropdown** ไม่ปล่อยให้ผู้ใช้พิมพ์คำถามยาวแล้วค่อยเจอ 503
- **`aiReady` ยังเป็น true ถ้ามีอย่างน้อยหนึ่งเจ้าที่ใช้ได้** — ตั้ง Claude ไว้แต่ไม่ตั้ง Gemini
  เป็นสถานะใช้งานได้จริง ไม่ใช่ความผิดพลาด แต่ `/api/chat/status` และ `/api/health`
  รายงานทีละรายด้วยเพื่อให้ผู้ดูแลเห็นว่าขาดตัวไหน
- **สลับผู้ให้บริการกลางบทสนทนาได้** เพราะ `ChatMessages.ModelName` เก็บเป็นรายข้อความ
  แต่ถ้าไม่ระบุโมเดล บทสนทนาจะอยู่กับเจ้าล่าสุดของมันเอง
- **เรียกผ่าน REST ตรง ไม่ใช้ SDK** เพราะ Google ไม่มี .NET SDK ทางการสำหรับ Gemini Developer API
  (มีแต่ Python/Node/Go/Java) — จะเพิ่ม dependency ของชุมชนมาให้ต้องไว้ใจ เพื่อ field แค่ไม่กี่ตัว
  ก็ไม่คุ้ม `Gemini:BaseUrl` แยกเป็นค่าตั้งไว้ให้ชี้ไป proxy ภายในองค์กรได้

### เพิ่มผู้ให้บริการรายที่สามในอนาคต

1. เขียนคลาสที่ implement `IAiProvider` (มี `ProviderName`, `IsConfigured`, `DefaultModel`, `CompleteAsync`)
2. `builder.Services.AddSingleton<IAiProvider, ...>();` ใน `Program.cs` หนึ่งบรรทัด
3. เพิ่มชื่อใน `AiProviders.All` และใน CHECK constraint ของฐานข้อมูล

`ChatService` ไม่ต้องแก้ เพราะคุยกับ `IAiClient` (ตัวจัดเส้นทาง) ไม่ได้คุยกับเจ้าใดเจ้าหนึ่ง

## 6.19 ผู้ให้บริการ AI รายที่สาม — OpenAI (ChatGPT)

เพิ่มเข้ามาโดยไม่ต้องแก้ `ChatService` เลย ตามที่โครงสร้างในข้อ 6.18 ออกแบบไว้ —
คลาสใหม่ที่ implement `IAiProvider`, DI หนึ่งบรรทัด, ค่าคงที่ใน `AiProviders`,
และขยาย CHECK constraint (`08_openai_provider.sql`)

### ต้องทำอะไรก่อนใช้

ใส่ OpenAI API key (ขอจาก platform.openai.com) ที่ `OpenAI:ApiKey` ใน
`appsettings.Development.json` หรือ environment variable `OPENAI_API_KEY`

```bash
setx OPENAI_API_KEY "sk-proj-..."
```

ไม่ใส่ก็ใช้ระบบได้ปกติ โมเดล `gpt-*` จะขึ้นป้าย "no API key" และตอบ 503 ถ้าเลือก
เหมือนกับ Gemini

### โมเดลที่ใส่ราคาไว้

ราคาจาก [developers.openai.com/api/docs/pricing](https://developers.openai.com/api/docs/pricing)
ตรวจเมื่อ 8 ก.ย. 2026 (USD ต่อ 1 ล้าน token) และ**ยิงทดสอบทีละตัวกับ key จริงแล้ว**

| โมเดล | Input | Output | Cache อ่าน | สถานะ |
|---|--:|--:|--:|---|
| `gpt-5-nano` | 0.05 | 0.40 | 0.005 | ปิดไว้ — ถูกที่สุดในระบบ แต่เป็นรุ่นปี 2025 |
| `gpt-5.6-luna` | 0.20 | 1.20 | 0.020 | **เปิด** — รุ่นประหยัด ไม่ใช้ reasoning token |
| `gpt-4.1-mini` | 0.40 | 1.60 | 0.100 | ปิดไว้ — รุ่นเก่าที่ไม่รับพารามิเตอร์ reasoning |
| `gpt-5.4-mini` | 0.75 | 4.50 | 0.075 | ปิดไว้ |
| `gpt-5.6-terra` | 2.00 | 12.00 | 0.200 | **เปิด** — รุ่นกลาง |
| `gpt-5.4` | 2.50 | 15.00 | 0.250 | ปิดไว้ |
| `gpt-5.5` | 5.00 | 30.00 | 0.500 | **เปิด** — รุ่นเรือธง |
| `gpt-6-astra` | 10.00 | 50.00 | 1.000 | ปิดไว้ — ราคาเท่า `claude-fable-5-1` |

`gpt-5.6-luna` เป็น**โมเดลที่ถูกที่สุดในระบบทั้งหมด** (0.031 บาทต่อคำถาม) ในบรรดาที่เปิดใช้อยู่
ไม่นับ `gpt-5-nano` ที่ปิดไว้ (0.010 บาท) — เปิดได้เองจากหน้า Model pricing

ไม่ใส่ `gpt-5.5-pro` / `gpt-5.4-pro` (30 / 180 USD) เพราะแพงกว่าที่งานนี้ต้องใช้มาก
และหน้า pricing ระบุว่าไม่มีราคา cached input ให้

### ใช้ Responses API ไม่ใช่ Chat Completions

เรียก `POST /v1/responses` เพราะเป็นพื้นผิวที่ OpenAI แนะนำสำหรับงานใหม่ และรองรับทั้ง
โมเดลที่มี reasoning กับไฟล์แนบในรูปแบบ request เดียว
(`input_image` สำหรับรูป, `input_file` สำหรับ PDF — ทดสอบแล้วว่าอ่าน PDF ได้จริง)

ส่ง `store: false` ไปทุกครั้ง — บทสนทนาถูกเก็บในฐานข้อมูลของเราอยู่แล้ว
การทิ้งสำเนาไว้ที่ผู้ให้บริการภายนอกเพิ่มพื้นที่ความเสี่ยงตาม PDPA โดยไม่ได้อะไรกลับมา

### กับดักการนับ token ที่ต่างกันทุกเจ้า

**จุดนี้สำคัญที่สุดของหัวข้อนี้** — ทั้งสามเจ้ารายงาน token ไม่เหมือนกัน
ถ้าลอกโค้ดจากเจ้าหนึ่งไปใช้กับอีกเจ้าจะคิดเงินผิดแบบเงียบ ๆ

| | Anthropic | Google Gemini | OpenAI |
|---|---|---|---|
| **cache token อยู่ใน input?** | แยกมาให้แล้ว | **รวมอยู่** ต้องหักออก | **รวมอยู่** ต้องหักออก |
| **token ของการคิดอยู่ใน output?** | รวมแล้ว | **แยก** (`thoughtsTokenCount`) ต้องบวกเข้า | **รวมแล้ว** ห้ามบวกซ้ำ |
| **ค่าเขียน cache** | คิด 1.25x ของ input | ไม่คิด | ไม่คิด |

ยืนยันด้วยการวัดจริง ไม่ใช่อ่านจากเอกสาร:

- OpenAI: prompt 10,027 token ยิงซ้ำครั้งที่สองได้ `cached_tokens` 10,024 โดย `input_tokens`
  ยังเป็น 10,027 เท่าเดิม และ `total == input + output` → cache รวมอยู่ใน input
- OpenAI: `output_tokens` 18 โดยมี `reasoning_tokens` 11 อยู่ในนั้น และ `total == input + output`
  → reasoning รวมอยู่ใน output แล้ว ถ้าบวกอีกจะคิดเงินเกินทุกครั้งที่โมเดลคิด

ชุดทดสอบตรวจตัวเลขนี้ทั้งสองทาง: เทียบยอด USD ที่ระบบบันทึกกับที่คำนวณมือจากราคาในตาราง
ทั้งกับโมเดลที่ไม่ใช้ reasoning และโมเดลที่ใช้ reasoning จริง

### พารามิเตอร์ reasoning — self-healing เป็นครั้งที่สาม

ตระกูล `gpt-5` รับ `reasoning.effort` แต่รุ่นเก่าอย่าง `gpt-4.1-mini` ตอบ

```
400 code=unsupported_parameter param=reasoning.effort
```

ระบบตรวจจากรหัสและชื่อพารามิเตอร์ใน error (ไม่ใช่จับข้อความ ซึ่งเปลี่ยนได้)
แล้วยิงใหม่โดยไม่ใส่ พร้อมจำโมเดลนั้นไว้ไม่ให้เสียรอบซ้ำ

นับเป็นครั้งที่สามที่รูปแบบนี้ได้ใช้ — `effort` ของ Anthropic, `thinkingLevel` ของ Gemini,
และตัวนี้ ยืนยันว่าการ **ไม่** ฮาร์ดโค้ดตารางความสามารถของโมเดลเป็นการตัดสินใจที่ถูก

### สองบั๊กที่พบตอนต่อ API จริง (แก้แล้วทั้งคู่)

1. **`"incomplete_details": null` ทำให้ทั้ง response พัง** — คำตอบที่สำเร็จมีฟิลด์นี้เป็น `null`
   และการเรียก `TryGetProperty` บน JSON null จะ throw `InvalidOperationException`
   คำตอบที่ดีสมบูรณ์จึงกลายเป็น HTTP 502 แก้โดยเพิ่มตัวช่วย `TryObject` ที่ลงไปในลูก
   เฉพาะเมื่อเป็น object จริง แล้วใช้กับทุกจุดที่อ่านฟิลด์ซ้อน **รวมถึงใน `GeminiClient` ด้วย**
   ซึ่งมีความเสี่ยงเดียวกันแฝงอยู่แต่ยังไม่เคยระเบิด
2. **ลืมแก้ validation ของ DTO** — เพิ่ม `OpenAI` ใน `AiProviders.All` และ CHECK constraint แล้ว
   แต่ `[RegularExpression("^(?i)(Anthropic|Google)$")]` บน `ModelPricingUpsertRequest` ยังเดิม
   ทำให้**แก้ราคาโมเดล OpenAI ไม่ได้เลย** โดยขึ้น error ว่า "must be Anthropic or Google"
   แก้โดยเปลี่ยนไปใช้ `AiProviderAttribute` ที่อ่านรายชื่อจาก `AiProviders.All` ตรง ๆ —
   ผู้ให้บริการรายที่สี่จะไม่ต้องแก้ไฟล์ DTO อีก

## 6.20 ทำกราฟจากข้อมูลในแชท

พิมพ์ตัวเลขในคำถาม หรือแนบไฟล์ Excel/CSV แล้วสั่ง "ทำกราฟให้ดู" คำตอบจะมีกราฟจริง
วาดอยู่ในบทสนทนา

### โมเดลส่ง "ข้อมูล" ไม่ใช่ "โค้ด"

โมเดลตอบกลับมาเป็น fenced block ชื่อ `chart` ที่มีแต่ JSON:

````
```chart
{"type":"bar","title":"ยอดขายรายไตรมาส","unit":"บาท",
 "labels":["Q1","Q2","Q3","Q4"],
 "series":[{"name":"ยอดขาย","values":[1200000,1850000,1430000,2100000]}]}
```
````

แล้ว `ChartBlock.jsx` วาดเป็น SVG เอง **ไม่มีการรันโค้ดจากโมเดลเลย** ทางเลือกอื่นคือให้โมเดล
เขียนโค้ดวาดกราฟแล้วเรารันให้ ซึ่งเท่ากับรันโค้ดที่ไม่ได้ตรวจในเบราว์เซอร์ของพนักงาน

การเก็บเป็น spec ยังได้อีกสองอย่าง: กราฟอยู่ใน `ChatMessages.Content` จึง **เปิดแชทเก่าแล้ว
กราฟยังวาดใหม่ได้เหมือนเดิม** และ **ผู้ตรวจสอบเห็นตัวเลขชุดเดียวกับที่พนักงานเห็น** ในหน้าค้น log
ไม่ใช่เห็นแค่รูปที่ตรวจย้อนกลับไม่ได้

ตั้งข้อความสอนรูปแบบนี้ได้ที่ `Claude:ChartSystemPrompt` — เป็นค่าตั้งแยกเพราะ schema
ต้องตรงกับที่ frontend อ่าน ถ้าไปแปะไว้ใน prompt ของทั้งสองโหมดจะกลายเป็นสองสำเนาที่เพี้ยนกัน
เมื่อแก้ที่เดียว เว้นว่างไว้ = ปิดการทำกราฟ

### ชนิดที่รองรับ

| type | ใช้เมื่อ |
|---|---|
| `bar` | เทียบขนาดข้ามหมวด |
| `hbar` | เหมือน bar แต่ชื่อหมวดยาว |
| `line` | การเปลี่ยนแปลงตามเวลา |
| `pie` | สัดส่วนของทั้งหมด — 3 ถึง 6 ชิ้นเท่านั้น |

รองรับได้ถึง 6 ชุดข้อมูลและ 40 หมวดต่อกราฟ

### กติกาการอ่านที่บังคับไว้ในตัววาด

ไม่ได้ปล่อยให้โมเดลกำหนดหน้าตา ตัววาดบังคับกติกาเหล่านี้เอง:

- **สีถูกกำหนดตามลำดับชุดข้อมูล ไม่วนซ้ำ** ลำดับสีเป็นกลไกความปลอดภัยสำหรับคนตาบอดสี
  ไม่ใช่เรื่องความสวย — ชุดที่ใช้ผ่านเกณฑ์คู่สีที่อยู่ติดกันทั้งแบบตาปกติและตาบอดสี
  (ตรวจด้วยสคริปต์ ไม่ได้ใช้สายตาตัดสิน) เกิน 6 ชุดจะไม่แต่งสีใหม่ให้ แต่ตัดออกพร้อมบอกไว้
- **มี legend ทุกครั้งที่มี 2 ชุดขึ้นไป** และ **ไม่มี legend เมื่อมีชุดเดียว** (ชื่อกราฟบอกอยู่แล้ว
  ช่องสีเดียวเปลืองที่เปล่า ๆ)
- **ติดป้ายตัวเลขแบบเลือกจุด ไม่ใส่ทุกจุด** — ป้ายบนทุกแท่งคือความรกที่ไม่มีใครอ่าน
  ตัววาดติดที่ค่าสูงสุด แล้วให้แกนกับ tooltip รับที่เหลือ
- **แกน Y ปัดเป็นเลขกลม** (0 / 500K / 1M) และมี **ปุ่มดูตารางข้อมูล** ทุกกราฟ —
  ตารางไม่ใช่ของแถม: สามสีในชุดมี contrast ต่ำกว่า 3:1 บนพื้นขาว ซึ่งบังคับให้ต้องมี
  ป้ายที่อ่านได้หรือตารางเป็นทางสำรอง
- **แท่งหนาไม่เกิน 24px** ปลายด้านข้อมูลมน ปลายด้านฐานตรง และเว้นช่องว่างสีพื้น 2px
  ระหว่างแท่งที่ติดกัน (ใช้ช่องว่างแยก ไม่ใช่ตีกรอบรอบแท่ง)
- **เส้นกริดเป็นเส้นทึบบาง ๆ ไม่ใช้เส้นประ** เส้นประอ่านเป็น "ค่าประมาณ" ทั้งที่เป็นแค่กริด
- **ตัวหนังสือไม่ใส่สีของข้อมูล** สีอยู่บนแท่ง/เส้น/จุด ส่วนตัวเลขและป้ายใช้สีตัวอักษรปกติ
  (สีอ่อนอย่างเหลืองอ่านเป็นตัวหนังสือไม่ออกบนพื้นขาว)

### กรณีที่ตัววาดเปลี่ยนรูปแบบให้เอง

- **แท่งเดียวจากข้อมูลจุดเดียว → แสดงเป็นตัวเลขใหญ่** เพราะกราฟแท่งเดียวก็คือตัวเลขนั้นเอง
- **pie ที่มีน้อยกว่า 3 หรือมากกว่า 6 ชิ้น → วาดเป็นแท่งแทน** พร้อมบอกเหตุผล
  (น้อยกว่า 3 ไม่มี "ทั้งหมด" ให้อ่าน มากกว่า 6 แยกชิ้นด้วยตาไม่ออก)
- **spec ที่ผิดรูปแบบ → แสดงเป็นบล็อกโค้ดพร้อมบอกว่าพังตรงไหน** ไม่ทำให้คำตอบทั้งข้อหาย

### สองอย่างที่กันไว้เรื่องความถูกต้องของข้อมูล

1. **ค่าที่ขาด (`null`) ถูกปฏิเสธ ไม่ถูกวาดเป็นศูนย์** — `Number(null)` ใน JavaScript เท่ากับ 0
   ถ้าไม่ดักไว้ เซลล์ว่างจะกลายเป็นแท่งค่าศูนย์ที่ดูเหมือนข้อมูลจริง ซึ่งบิดเบือนข้อมูล
   (เจอตอนทดสอบด่านตรวจ spec)
2. **prompt สั่งห้ามแต่งตัวเลข** — ถ้าไม่มีข้อมูลให้ โมเดลต้องบอกว่าไม่มี ไม่ใช่ประมาณขึ้นมาวาด
   ทดสอบแล้วว่าขอ "กราฟยอดขายรายเดือนปีนี้" ลอย ๆ โมเดลตอบขอข้อมูลก่อน ไม่วาดกราฟ

## 6.21 ส่งออกคำตอบเป็นรายงาน Excel / PDF / Word / PowerPoint

ใต้คำตอบของ AI ทุกข้อมีปุ่ม **Export: Excel · PDF · Word · PowerPoint** กดแล้วได้ไฟล์
ของคำตอบนั้นทันที ไม่ต้องคัดลอกไปวางเอง

`GET /api/chat/messages/{id}/export/{xlsx|pdf|docx|pptx}`

### สรุปด้วย prompt แล้วค่อยส่งออก

พอผู้ใช้ขอ "ทำรายงาน" หรือบอกว่าจะเอาไป export ระบบจะปลดเพดานความยาวคำตอบให้
(prompt ปกติจำกัดไว้ 6 บรรทัดเพื่อให้แชทเร็ว — ถ้าไม่ปลด รายงานที่ export ออกมา
จะได้เอกสาร 6 บรรทัด) และสั่งให้โมเดลจัดโครงสร้างเป็นหัวข้อ ตาราง และ bullet
เพราะโครงสร้างนั้นคือสิ่งที่ตัวเขียนไฟล์นำไปใช้ได้จริง

ตั้งข้อความนี้ได้ที่ `Claude:ReportSystemPrompt` (เว้นว่าง = ปิด)

### ไม่ต้องให้โมเดลเรียนรูปแบบใหม่

ตัวแปลงอ่าน **คำตอบที่มีอยู่แล้ว** แล้วแยกเป็นบล็อก — หัวข้อ `#`, ย่อหน้า, bullet,
ตาราง `| a | b |`, fenced code และ **กราฟจาก `chart` block ที่ทำไว้ในข้อ 6.20**
จึงส่งออกคำตอบไหนก็ได้ ไม่ใช่เฉพาะคำตอบที่โมเดลตั้งใจทำเป็นรายงาน และการอ่านใช้กติกา
เดียวกับที่หน้าแชทใช้ ไฟล์ที่ได้จึงตรงกับที่พนักงานเห็นบนจอ

**กราฟกลายเป็นตารางตัวเลข** พร้อมหมายเหตุว่า "shown as a chart in the conversation" —
คนอ่านรายงานต้องการตัวเลขไปใช้ต่อ และการวาดรูปกราฟซ้ำในสี่รูปแบบไฟล์คือเครื่องจักร
จำนวนมากเพื่อผลลัพธ์ที่ด้อยกว่าตาราง (ใน Excel ตัวเลขยังเป็นตัวเลขจริง `SUM` และเรียงได้)

### แต่ละรูปแบบได้อะไร

| รูปแบบ | โครงสร้าง |
|---|---|

## 6.2 ลากไฟล์มาให้ AI วิเคราะห์

พนักงานลากไฟล์มาวางในหน้าแชท กดปุ่ม 📎 หรือ **วางจาก clipboard (Ctrl+V)** ได้
พิมพ์ข้อความหรือไม่พิมพ์ก็ได้ — ถ้าแนบไฟล์เปล่า ๆ ระบบจะใส่คำสั่ง "ช่วยวิเคราะห์และสรุปสาระสำคัญ
ของไฟล์ที่แนบมา" ให้เอง

| ชนิด | นามสกุล | ส่งให้ AI แบบ | คัดกรอง policy จากเนื้อหา |
|---|---|---|:--:|
| ไฟล์ข้อความ | `.txt` `.csv` `.md` `.json` `.log` | document (plain text) | **ได้** |
| PDF | `.pdf` | document (base64) | ไม่ได้ — คัดกรองได้แค่ชื่อไฟล์ |
| รูปภาพ | `.png` `.jpg` `.jpeg` `.webp` `.gif` | image block | ไม่ได้ — คัดกรองได้แค่ชื่อไฟล์ |

ข้อจำกัดตั้งต้น (ปรับที่ section `Uploads` ใน appsettings): 15 MB ต่อไฟล์, 5 ไฟล์ต่อข้อความ,
รวมไม่เกิน 25 MB ต่อข้อความ, ไฟล์ข้อความยาวเกิน 200,000 ตัวอักษรจะถูกตัดพร้อมระบุไว้ในเนื้อหา

### สิ่งที่ระบบทำกับไฟล์

1. **ตรวจก่อนรับ** — นามสกุลต้องอยู่ในรายการที่อนุญาต, ขนาดไม่เกินขีด, และ **ตรวจ magic bytes**
   ว่าเนื้อหาตรงกับนามสกุลจริง (เปลี่ยนชื่อ `.exe` เป็น `.pdf` จะถูกปฏิเสธ)
2. **เก็บลง disk** ที่ `Uploads:RootPath` แยกโฟลเดอร์ตามปี/เดือน/วัน ตั้งชื่อไฟล์เป็น GUID
   (ชื่อเดิมเก็บใน DB — กันชื่อไฟล์ชนกันและกันชื่อไฟล์ที่เป็นอันตราย)
3. **คัดกรองตาม PolicyRules** จาก *ข้อความ + ชื่อไฟล์ทุกไฟล์ + เนื้อหาของไฟล์ข้อความ
   และเซลล์ในไฟล์ Excel* รวมกัน — ไฟล์ที่มีรหัสผ่านหรือเลขบัตรประชาชนจะถูกบล็อก
   เหมือนพิมพ์ลงในแชทตรง ๆ
4. **บันทึก metadata + SHA-256** ลง `ChatAttachments` และลง audit `FILE_UPLOADED`
   (ระบุชื่อ ชนิด ขนาด hash และว่าคัดกรองเนื้อหาได้หรือไม่)
5. **ส่งให้ผู้ให้บริการที่เลือก** โดยวางไฟล์ไว้ก่อนข้อความ ตามคำแนะนำของ Anthropic
   (ทำเหมือนกันทั้งสามเจ้า)
6. **เปิด prompt cache อัตโนมัติเมื่อบทสนทนามีไฟล์แนบ** — เอกสารเดิมถูกส่งซ้ำทุกตาเพื่อให้
   ถามต่อเนื่องได้ การอ่านจาก cache คิดราคาเพียง 0.1x ของ input (วัดจริงกับ CSV 400 บรรทัด:
   เขียน 13,204 token แล้วคำถามถัดไปอ่านคืน 13,204 token)

   **ข้อจำกัดที่ต้องรู้:** prompt cache มีขั้นต่ำความยาว prompt (~1,024 token) เอกสารสั้น ๆ
   จึงไม่ถูก cache แม้ระบบส่ง `cache_control` ไปแล้ว และขั้นต่ำนี้ **ต่างกันตามโมเดล** —
   ที่วัดได้ `claude-opus-5` cache เอกสารขนาด ~324 token ได้ แต่ `claude-sonnet-5` ไม่ทำ
   (พอเอกสารยาวเกินขั้นต่ำ ทั้งสองโมเดล cache เหมือนกัน) ไม่กระทบความถูกต้อง กระทบแค่ค่าใช้จ่าย
   ของการถามต่อเนื่องเกี่ยวกับเอกสาร **สั้น**

### ไฟล์ Excel (.xlsx / .xls)

**ไม่มีผู้ให้บริการ AI รายไหนอ่าน workbook ได้เอง** — Anthropic รับ PDF กับข้อความ, Gemini
รับ PDF กับรูป, `input_file` ของ OpenAI รับ PDF ส่งไฟล์ .xlsx ดิบไปให้เจ้าไหนก็ตาม
ผลคือเรียกไม่สำเร็จหรือไฟล์ถูกเมิน

ระบบจึง **สกัดเซลล์เป็นข้อความฝั่งเซิร์ฟเวอร์** (ผ่าน `ExcelDataReader` ซึ่งอ่านได้ทั้ง
.xlsx และ .xls รุ่นเก่า) แล้วส่งเป็นเอกสารข้อความ — โค้ดทางเดียวใช้ได้กับทั้งสามเจ้า
และได้ผลพลอยได้ที่สำคัญกว่า: **เนื้อหาในเซลล์ถูกคัดกรองตาม PolicyRules** เหมือนไฟล์ `.csv`
ไม่ใช่ดูได้แค่ชื่อไฟล์อย่าง PDF กับรูปภาพ (ทดสอบแล้วว่า workbook ที่มีคำว่า "รหัสผ่าน:"
ในเซลล์ถูกบล็อกจริง)

**ไฟล์ต้นฉบับยังถูกเก็บบน disk ครบทุกไบต์** — ผู้ตรวจสอบดาวน์โหลดไป
เปิดใน Excel ได้ตามปกติ ไม่ได้ได้แค่ข้อความที่สกัด

รูปแบบข้อความที่ส่งให้โมเดล:

```
--- Sheet: Stock (4 rows) ---
Code | Item | จำนวน | หน่วย | Received
CH-0001 | โซดาไฟ 98% | 120 | ถุง | 2026-08-01
```

จุดที่ตั้งใจทำแบบนี้:

- **คั่นด้วย `|` ไม่ใช่จุลภาค** เพราะเซลล์มีจุลภาคได้เอง โมเดลอ่าน `a,b,c` แล้วแยกไม่ออกว่า
  เป็นสองคอลัมน์ที่มีจุลภาคอยู่ข้างใน หรือสามคอลัมน์
- **มีชื่อชีตกำกับ** เพราะ workbook เดียวมีหลายชีต ถ้าไม่บอกโมเดลจะอ้างที่มาของตัวเลขไม่ได้
- **ข้ามชีตและแถวว่าง** — workbook ทั่วไปมีแถวว่างท้ายชีตเป็นพันแถว ส่งไปก็เสีย token เปล่า
- **วันที่เป็น `yyyy-MM-dd`** ตัดเวลา `00:00:00` ที่ไม่มีความหมายออก และตัวเลขใช้ `G15`
  ไม่ให้กลายเป็น scientific notation
- **`.xlsm` ไม่อนุญาตโดยเจตนา** — ไฟล์ที่มี macro เป็นความเสี่ยงด้านการรันโค้ด และระบบอ่านแค่
  เซลล์อยู่แล้ว ถ้าจำเป็นจริงก็เพิ่มใน `Uploads:AllowedExtensions` ได้
- **ตรวจสองด่าน** — `.xlsx` เป็นไฟล์ zip จึงมี magic bytes เหมือน zip อื่นทุกชนิด
  ด่าน magic bytes จับได้แค่ "ไม่ใช่ zip เลย" (เช่น `.exe` เปลี่ยนชื่อ) ส่วนด่านจริงคือ
  **ตัวอ่านต้อง parse เป็น workbook ได้** ไม่ได้ก็ปฏิเสธพร้อมบอกทางแก้
- **`Uploads:MaxSpreadsheetRows`** (ตั้งต้น 2,000 แถวต่อชีต) กันไฟล์ zip ที่ขยายเป็นข้อความ
  มหาศาล — ไฟล์ 2 MB อาจกลายเป็นข้อความหลายสิบล้านตัวอักษร ทั้งกินหน่วยความจำและค่า token
  เกินเพดานแล้วจะต่อท้ายว่าถูกตัด ไม่ใช่เงียบ ๆ ส่งไปครึ่งเดียว

### ข้อจำกัดที่ต้องรู้

- **เนื้อหาใน PDF และรูปภาพไม่ถูกคัดกรองตาม policy** — ระบบทำได้แค่ตรวจชื่อไฟล์
  (ไฟล์ข้อความและ **Excel** ถูกคัดกรองจากเนื้อหาจริง)
  หน้าค้น log จึงติดป้าย **"ไม่สแกน"** กำกับไฟล์เหล่านี้ และหน้าแชทเตือนผู้ใช้ไว้ด้านล่างช่องพิมพ์
  ถ้าต้องการปิดช่องนี้จริงจัง ทางเลือกคือ (ก) เอา `.pdf` และนามสกุลรูปออกจาก `AllowedExtensions`
  หรือ (ข) เพิ่มการทำ OCR/สกัดข้อความจาก PDF ก่อนคัดกรอง (ยังไม่ได้ทำ)
- **ไฟล์ที่ถูก policy บล็อกยังถูกเก็บไว้** โดยเจตนา เพื่อให้ผู้ตรวจสอบเห็นว่าพนักงาน
  *พยายาม* ส่งอะไรออกไป — ไฟล์นั้นไม่เคยถูกส่งให้ AI
- ไฟล์แนบทำให้ token ต่อข้อความสูงขึ้นชัดเจน ดูผลกระทบด้านค่าใช้จ่ายได้ที่หน้ารายงานค่าใช้จ่าย

### การเข้าถึงไฟล์ย้อนหลัง

`GET /api/chat/attachments/{id}` — **เจ้าของไฟล์ หรือ Admin/Auditor** เท่านั้น
และการเปิดไฟล์ทุกครั้งถูกบันทึกเป็น `FILE_DOWNLOADED` พร้อมระบุว่าใครเปิดไฟล์ของใคร
หน้าค้น log แสดงไฟล์แนบเป็นชิปที่คลิกดาวน์โหลดได้ และมีตัวกรอง **"เฉพาะข้อความที่มีไฟล์แนบ"**
(`hasAttachments=true`) พร้อมคอลัมน์จำนวน/ชื่อไฟล์ในไฟล์ CSV ที่ export

## 6.22 ทะเบียนแหล่งข้อมูลภายนอก + สิทธิ์รายผู้ใช้ (Backoffice)

Admin/IT ลงทะเบียนแหล่งข้อมูลไว้ที่หน้า **Data source registry** แล้วกำหนดว่าพนักงานคนไหน
อ่านได้แค่ไหนที่หน้า **Data source access** — สองหน้านี้เป็นทะเบียนกับตารางสิทธิ์เท่านั้น
ส่วนการดึงข้อมูลจริงเข้าไปให้ AI วิเคราะห์ในแชท (Phase 2) อยู่ที่หัวข้อ **6.23** ถัดไป

"IT" ในที่นี้คือใครก็ตามที่ถือบทบาท **Admin** — ระบบนี้ไม่มีบทบาท "IT" แยกต่างหาก

### สี่ชนิดแหล่งข้อมูล

| ชนิด | ตัวอย่างการใช้งาน | ทดสอบเชื่อมต่อได้จริงไหม |
|---|---|---|
| **API** | SAP OData, ระบบภายในที่มี REST API | **ได้จริง** — ยิง HTTP ไปที่ baseUrl พร้อม auth ที่ตั้งไว้ |
| **SharePoint** | ไซต์เอกสารของแผนก | **ได้จริง** — OAuth2 client-credentials กับ Entra ID แล้วเรียก Microsoft Graph |
| **โฟลเดอร์ในเครื่อง/เครือข่าย** | โฟลเดอร์แชร์บน server, UNC path | **ได้จริง** — ตรวจว่าโฟลเดอร์มีอยู่และเซิร์ฟเวอร์อ่านได้ |
| **Data Lake / Lakehouse** | Microsoft Fabric — semantic model (Power BI) หรือ Warehouse/Lakehouse (SQL) | **ได้จริง** — OAuth2 client-credentials กับ Entra ID (คนละ scope ต่อโหมด) แล้วรัน DAX ผ่าน Power BI REST API หรือ T-SQL ผ่าน SQL endpoint |

**Data Lake ต่อ Microsoft Fabric ได้สองแบบ**, เลือกต่อ source ผ่านฟิลด์ `connectionMode`:

1. **`PowerBi` (ค่า default)** — ยิง DAX query ไปที่ **Power BI REST API's Execute Queries
   endpoint** (`POST /v1.0/myorg/datasets/{id}/executeQueries`) โดยใช้ token แบบ client-credentials
   (scope `EntraAuth.PowerBiScope`) ตั้งค่าที่ต้องกรอกเพิ่ม: `datasetId` (GUID ของ semantic model —
   ดูได้จากหน้า Settings ของ model ใน Fabric/Power BI), `daxQuery` (คำสั่งที่จะรันทุกครั้งที่ดึง
   ข้อมูล เช่น `EVALUATE 'Sales'`)
2. **`Warehouse`** — เชื่อมต่อ **Fabric Warehouse/Lakehouse SQL analytics endpoint** โดยตรงด้วย
   `Microsoft.Data.SqlClient` (`SqlConnection.AccessToken` รับ token จาก client-credentials เดียวกัน
   แต่คนละ scope — `EntraAuth.SqlScope` = `https://database.windows.net/.default`) แล้วรัน T-SQL
   ที่ตั้งไว้ตรง ๆ ผลลัพธ์ถูกแปลงเป็นตาราง Markdown ก่อนส่งให้ AI ตั้งค่าที่ต้องกรอกเพิ่ม:
   `sqlEndpoint` (โฮสต์เนมล้วน เช่น `xxxx.datawarehouse.fabric.microsoft.com` — ไม่ต้องใส่ `tcp:`
   หรือ port), `database` (ชื่อ warehouse/lakehouse), `sqlQuery` (คำสั่ง SELECT ที่จะรันทุกครั้ง)

ทั้งสองโหมดใช้ `tenantId`, `clientId` (Entra app) และ Secret (client secret ของ Entra app) ร่วมกัน —
source ที่สร้างไว้ก่อนมีฟิลด์นี้ (ไม่มี `connectionMode` เลย) ยังทำงานเหมือนเดิมทุกประการ (เท่ากับ
`PowerBi` โดย default)

**สองเงื่อนไขที่ระบบตรวจให้ไม่ได้ ต้องให้ IT/Fabric admin จัดการเอง (ทั้งสองโหมด):**
1. Entra ID app registration ต้องมีสิทธิ์ที่ถูกต้อง — Power BI Service API (เช่น
   `Dataset.Read.All`) สำหรับโหมด `PowerBi`, หรือสิทธิ์อ่านข้อมูลใน SQL endpoint นั้น (grant ให้
   service principal โดยตรง) สำหรับโหมด `Warehouse`
2. Fabric admin ต้องเปิด **"Allow service principals to use Fabric APIs"** ในหน้า Fabric admin
   portal (ทั้ง tenant หรือจำกัดเฉพาะ security group ก็ได้) — ถ้าไม่เปิด Fabric จะปฏิเสธทุก
   client-credentials call เงียบ ๆ ด้วย 401/403 โดยไม่บอกสาเหตุ ซึ่งข้อความ error ของ connector
   นี้จะเตือนถึงจุดนี้โดยเฉพาะเมื่อเจอ 401/403

### ขอบเขตสิทธิ์ (Scope) — ตอบสองตัวอย่างที่ผู้ใช้ให้มาโดยตรง

| Scope | พฤติกรรม | ตรงกับตัวอย่าง |
|---|---|---|
| **Full** | อ่านได้ทั้งหมดที่แหล่งข้อมูลนั้นมี | — |
| **Custom** | แอดมินพิมพ์เงื่อนไขเป็นข้อความอิสระ | **CFO/CMO อ่าน SAP เฉพาะบาง endpoint** — พิมพ์ `/finance/*, /gl/*` ไว้ในช่อง scope filter |
| **Own department** | ผูกกับ `Users.Department` ของพนักงานคนนั้น — **เป็นแค่ label สำหรับผู้ให้สิทธิ์จำไว้เอง** | **Sales Manager เห็นเฉพาะ Division ตัวเอง** — แอดมินยังต้องพิมพ์เงื่อนไขจริงลง scope filter (ดู 6.23) เพราะการเดา "Division" จาก query string ของ API หนึ่ง กับ path ของโฟลเดอร์อีกอันนั้นไม่เหมือนกัน |

**Own department ปฏิเสธการให้สิทธิ์ ถ้าพนักงานคนนั้นยังไม่มีค่า Department** — ไม่ปล่อยให้
กลายเป็น "ไม่มีอะไรจำกัด" อย่างเงียบ ๆ (ถ้าไม่เช็คจุดนี้ เจตนาของแอดมินที่อยากจำกัดสิทธิ์จะ
กลายเป็น Full โดยไม่มีใครรู้ ตอนพนักงานคนนั้นบังเอิญยังไม่ได้กรอกแผนก)

> **สำคัญ (อัปเดตตอนต่อกับแชทจริงใน Phase 2):** `OwnDepartment` **ไม่ได้จำกัดข้อมูลที่ดึงมา
> โดยอัตโนมัติ** — ตัวที่จำกัดข้อมูลจริงตอนดึงเข้าแชทคือข้อความใน **Custom scope filter**
> เท่านั้น (ดู 6.23) ถ้าต้องการให้ Sales Manager เห็นเฉพาะ Division ตัวเอง ให้ตั้ง ScopeType
> เป็น **Custom** แล้วพิมพ์เงื่อนไขนั้นตรง ๆ ลงช่อง scope filter — เลือกออกแบบแบบนี้เพราะ
> "จำกัดตาม Department" มีความหมายไม่เหมือนกันเลยระหว่าง query parameter ของ API หนึ่ง กับ
> ชื่อโฟลเดอร์ย่อยของแหล่งข้อมูลอีกอัน การเดาอัตโนมัติจะผิดได้ง่ายกว่าการให้แอดมินพิมพ์เอง

**หนึ่งคนมีสิทธิ์ที่ "เปิดอยู่" ต่อแหล่งข้อมูลหนึ่งได้แค่แถวเดียว** — ให้สิทธิ์ใหม่ทับของเดิม
ระบบจะปิดแถวเก่าให้เอง (ไม่ลบทิ้ง) กันการตีความยากว่า scope ไหนเป็นตัวจริงเมื่อมีมากกว่าหนึ่งแถว

### ความลับไม่เคยเป็น plain text

API key / client secret / SharePoint app secret เข้ารหัสด้วย **ASP.NET Core Data Protection**
ก่อนเก็บลง `DataSources.EncryptedSecret` เสมอ — ตรวจแล้วด้วยการอ่านค่าตรงจากฐานข้อมูลว่า
ไม่มีความลับต้นฉบับหลงเหลืออยู่ และ response ของทุก endpoint ไม่เคยส่งความลับกลับมา
(มีแค่ `hasSecret: true/false`) แก้ไขแหล่งข้อมูลแล้วเว้นช่อง secret ว่างไว้ = คงค่าเดิม
ไม่ใช่ล้างทิ้ง (ส่งสตริงว่างต่างหากถ้าต้องการล้างจริง ๆ)

> **ข้อจำกัดที่ต้องรู้ก่อนขึ้น production:** กุญแจเข้ารหัสถูกเก็บเป็นไฟล์ที่
> `App_Data/keys` บนเครื่องที่รันแอป ถ้าขยายเป็นมากกว่าหนึ่งเครื่อง (load balancer)
> เครื่องที่สองจะถอดรหัสความลับที่เครื่องแรกเขียนไว้ไม่ได้ ต้องเปลี่ยนไปแชร์ key ring
> ผ่าน network path หรือ Azure Key Vault ก่อน (`AddDataProtection().PersistKeysToFileSystem(...)`
> ใน `Program.cs` เป็นจุดที่ต้องแก้)

### สิทธิ์และการตรวจสอบ

- ทั้งสองหน้าเป็นของ **Admin เท่านั้น** — Auditor เข้าไม่ได้ (ต่างจากหน้า log ที่ Auditor
  อ่านได้ เพราะนี่คือหน้าที่ *เปลี่ยนแปลง* ว่าใครเข้าถึงอะไรได้ ไม่ใช่หน้าดูประวัติ)
- **ลบแหล่งข้อมูลไม่ได้ถ้ามีประวัติ grant อยู่** (ทั้งที่ active และเพิกถอนแล้ว) — ต้อง
  เพิกถอนสิทธิ์ทั้งหมดก่อน หรือปิดใช้งาน (`isActive=false`) แทนการลบ กันไม่ให้ audit trail
  ลอยค้างชี้ไปยังแหล่งข้อมูลที่หายไปแล้ว
- **เพิกถอนสิทธิ์ = ปิดใช้งาน ไม่ลบแถวทิ้ง** (แบบเดียวกับ PolicyRules ที่ปิดไม่ลบ)
  บันทึกไว้ว่าใครเพิกถอนและเมื่อไหร่ ผู้ตรวจสอบย้อนดูได้เสมอว่าเคยให้สิทธิ์ใครไว้ตอนไหน
- ทุกการกระทำ (ลงทะเบียน แก้ไข ทดสอบเชื่อมต่อ ให้สิทธิ์ เพิกถอน) บันทึก audit log
  เป็น `DATASOURCE_CREATED` / `DATASOURCE_UPDATED` / `DATASOURCE_TESTED` /
  `DATASOURCE_GRANTED` / `DATASOURCE_REVOKED`

### ขยายต่อในอนาคต

เพิ่มชนิดแหล่งข้อมูลที่ห้า = คลาสใหม่ที่ implement `IDataSourceConnectionTester` **และ**
`IDataSourceFetcher` (ดู 6.23) + DI สองบรรทัด + เพิ่มชื่อใน `DataSourceTypes.All` และ CHECK
constraint ของฐานข้อมูล (แบบเดียวกับตอนเพิ่มผู้ให้บริการ AI รายที่สองและสาม)

## 6.23 ดึงข้อมูลจาก Data Source เข้าแชทจริง (Phase 2)

ต่อจากทะเบียน + สิทธิ์ใน 6.22 — พนักงานที่มี grant ที่ยัง active เลือกแหล่งข้อมูลได้ตอน
**เริ่มบทสนทนาใหม่** (ช่อง "Data source" ในหน้าแชท ข้าง ๆ ช่องเลือก Project) เหมือนกับที่
เลือก Project ได้ ระบบดึงข้อมูลมาให้ AI อ่านเป็นบริบทของบทสนทนานั้นทั้งเส้นทาง

### จังหวะการดึงข้อมูล

- **ดึงครั้งเดียวตอนเริ่มบทสนทนา** แล้วแคชผลไว้ที่ตาราง `ChatSessionDataFetches`
  (หนึ่งแถวต่อหนึ่งบทสนทนา) — ทุกข้อความถัดไปในบทสนทนาเดียวกันใช้ผลที่แคชไว้ซ้ำ
  ไม่ได้ยิงไปที่ปลายทางจริงซ้ำทุกครั้งที่พิมพ์คำถาม (เร็วกว่าและไม่เปลืองโควต้า API ปลายทาง)
- ผู้ใช้กดปุ่ม **"Refresh"** ที่แถบสถานะเหนือกล่องแชทเพื่อดึงข้อมูลใหม่ได้เอง — เขียนทับแถว
  เดิม ไม่เก็บประวัติการดึงแยก (audit log มี `DATASOURCE_FETCHED`/`DATASOURCE_FETCH_FAILED`
  ให้ไล่ย้อนดูอยู่แล้วว่าใครดึง/รีเฟรชเมื่อไหร่)
- ผูก Data Source กับบทสนทนาตอนสร้างเท่านั้น เปลี่ยนภายหลังไม่ได้ — เหตุผลเดียวกับ ProjectId

### กลไกส่งเข้า AI — ใช้ของเดิมที่มีอยู่แล้วทั้งหมด

ข้อมูลที่ดึงมา (ข้อความล้วน) ถูกห่อเป็น turn สังเคราะห์คู่หนึ่ง (user บอกว่า "นี่คือข้อมูลที่ดึงมา"
ตามด้วย assistant รับทราบสั้น ๆ) ผ่านกลไก `TurnAttachment`/`ChatTurn` ตัวเดียวกับที่ไฟล์แนบ
ข้อความและไฟล์อ้างอิงของ Project ใช้อยู่แล้ว — **ไม่ต้องแก้โค้ดเฉพาะผู้ให้บริการ AI รายใดเลย**
ทั้งสามราย (Claude/Gemini/OpenAI) อ่านได้เหมือนกันหมด และได้ prompt caching มาฟรีเหมือนไฟล์แนบ

### แต่ละชนิดแหล่งข้อมูลดึงอะไรจริง ๆ

| ชนิด | ดึงอะไร |
|---|---|
| **โฟลเดอร์ในเครื่อง/เครือข่าย** | อ่านไฟล์ `.txt/.csv/.md/.json/.log/.xlsx/.xls` ทุกไฟล์ใต้ path ที่ตั้งไว้ (หรือใต้ path ย่อยตาม scope filter) แปลงเป็นข้อความต่อกัน — Excel ใช้ตัวแปลงเดียวกับไฟล์แนบในแชท |
| **API** | ยิงตาม `method` ที่ตั้งไว้ (`GET` ค่าเริ่มต้น หรือ `POST` พร้อม `requestBody`) ไปที่ `baseUrl` ด้วย auth ที่ตั้งไว้ (เหมือนตอน Test connection) ต่อ scope filter เป็น query string ท้าย URL แล้วส่ง response body ทั้งก้อนเป็นข้อความให้ AI |
| **SharePoint** | sign-in แบบ client-credentials เดียวกับ Test connection แล้วเรียก Microsoft Graph ไล่อ่านไฟล์ในไลบรารีเอกสารของไซต์ (หรือใต้โฟลเดอร์ย่อยตาม scope filter) |
| **Data Lake / Lakehouse** | sign-in แบบ client-credentials เดียวกับ SharePoint (คนละ scope ต่อโหมด) แล้วรันตาม `connectionMode`: **`PowerBi`** — `daxQuery` ผ่าน Power BI Execute Queries API ส่ง JSON ผลลัพธ์ทั้งก้อนเป็นข้อความให้ AI; **`Warehouse`** — `sqlQuery` ผ่าน SQL endpoint ของ Fabric Warehouse/Lakehouse ตรง ๆ ด้วย `Microsoft.Data.SqlClient` แปลงผลลัพธ์เป็นตาราง Markdown ก่อนส่งให้ AI — ทั้งสองโหมด scope filter (ถ้ามี) จะ**แทนที่** query เดิมทั้งหมด แทนที่จะต่อท้าย เพราะทั้ง DAX และ SQL ที่พิมพ์เองไม่มีวากยสัมพันธ์ "เติม filter เข้าไปในคำสั่งเดิม" แบบ query string ของ URL |

ทุกตัวมี **เพดานขนาด** กันข้อมูลก้อนใหญ่ทำให้บทสนทนาบวมเกินไป: อย่างมาก 30 ไฟล์และ
120,000 ตัวอักษรต่อการดึงหนึ่งครั้ง (ไฟล์เดี่ยวเกิน 5 MB ถูกข้าม) เกินแล้วตัดพร้อมบอกผู้ใช้ว่า
"ตัดข้อมูลบางส่วนออกแล้ว" ไม่ใช่ทำให้ล้มทั้งการดึง

**แหล่งข้อมูลชนิด API ตั้งค่าเพิ่มเติมได้สามอย่าง** ในหน้า Data source registry:
- `method` — `GET` (ค่าเริ่มต้น) หรือ `POST`
- `requestBody` — JSON ดิบที่ส่งไปตรง ๆ เมื่อ `method = POST` เท่านั้น (ถูกละเว้นตอน GET) —
  ปล่อยว่างไว้ยังส่งเป็น `POST` พร้อม body `{}` และ header `Content-Type: application/json`
  เสมอ **ไม่ใช่ปล่อยว่างจริง ๆ** เพราะ API สไตล์ ASP.NET หลายตัว (รวมถึง backend ของแอปนี้เอง)
  ปฏิเสธ POST ที่ไม่มี Content-Type ด้วย `415 Unsupported Media Type` ก่อนจะดูเนื้อหา body ด้วยซ้ำ
- `timeoutMinutes` — ค่าเริ่มต้น 2 นาที ปรับได้ต่อแหล่งข้อมูล เพราะ endpoint รายงานภายในบางตัว
  (เช่น query ช่วงวันที่กว้าง ๆ) ใช้เวลาตอบกลับไม่คงที่และอาจนานกว่านั้นมาก — ค่านี้บังคับใช้
  ทั้งตอน "Test connection" และตอนดึงข้อมูลจริงเข้าแชท

### scope filter คือกลไกจำกัดข้อมูลจริง ไม่ใช่ ScopeType

ตามที่ตกลงกันตอนออกแบบ: ระบบ**ไม่มี automation ผูกกับ `Users.Department`**
ตัวที่จำกัดข้อมูลจริงคือข้อความใน **Custom scope filter** ที่แอดมินพิมพ์ไว้ตอนให้สิทธิ์ ใช้ตรง ๆ
ตามชนิดแหล่งข้อมูล:

- โฟลเดอร์/SharePoint: ตีความเป็น path ย่อย (เช่น `Sales` → เฉพาะโฟลเดอร์ Sales) — กันไม่ให้
  ทะลุออกนอก path/ไซต์ที่ตั้งไว้ (path traversal guard: `..` ที่พยายามหนีออกไปนอก root
  จะถูกปฏิเสธพร้อมข้อความชัดเจน ไม่ใช่แอบอ่านให้เงียบ ๆ)
- API: ตีความเป็น query string ต่อท้าย `baseUrl` ตรง ๆ (เช่น `division=Sales`) — แอดมินต้องรู้
  พารามิเตอร์ของ API ปลายทางเอง เพราะ "จำกัดตามแผนก" มีความหมายต่างกันในทุก API

ไม่มี scope filter (Full, หรือ Custom ที่เว้นว่างช่องนี้ไว้) = ดึงได้ทั้งหมดที่แหล่งข้อมูลนั้นมี
ภายใต้เพดานขนาดด้านบน

### สิทธิ์และการตรวจสอบ

- เห็นแหล่งข้อมูลในช่องเลือกตอนเริ่มแชทเฉพาะที่ **ตัวเองมี grant ที่ยัง active** เท่านั้น
  (`GET /api/chat/data-sources`) — Admin ไม่ได้เห็นทุกแหล่งข้อมูลอัตโนมัติแค่เพราะเป็น Admin
  ต้องมี grant ของตัวเองเช่นกัน (สอดคล้องกับเจตนาเดิมว่า "ใครอ่านส่วนไหนได้บ้าง" ต้องมีคนกำหนด
  ไว้ชัดเจนเสมอ)
- เพิกถอน grant แล้ว "Refresh" จะล้มด้วย 403 ทันที — บทสนทนาเดิมยังอ่านได้ (ข้อมูลที่แคชไว้
  ก่อนถูกเพิกถอนไม่ถูกลบ) แต่จะดึงข้อมูลใหม่ไม่ได้อีก
- ลบแหล่งข้อมูลไม่ได้ถ้ามีบทสนทนาใดผูกอยู่ (นอกเหนือจากเงื่อนไขเดิมเรื่องประวัติ grant) —
  ปิดใช้งานแทน (`isActive=false`)
- ทุกครั้งที่ดึง/รีเฟรชสำเร็จหรือล้มเหลว บันทึก audit log เป็น `DATASOURCE_FETCHED` /
  `DATASOURCE_FETCH_FAILED` ผูกกับ SessionId, SourceId และผู้ใช้ที่กดเสมอ

## 6.24 ตาราง Markdown เรนเดอร์เป็นตารางจริง

`MessageContent.jsx` จงใจ**ไม่ใช่** ตัวแปลง Markdown เต็มรูปแบบ (ดูคอมเมนต์ในไฟล์ — คำตอบของ AI
เป็น input ที่ไม่น่าเชื่อถือ ต้องเลี่ยงการทำ `innerHTML` จากข้อความที่แปลงมา) แต่เพิ่มการจับ
เฉพาะตาราง Markdown แบบ GFM (`| a | b |` ตามด้วยแถวคั่น `|---|---|`) แล้ววาดเป็น `<table>` จริง
ด้วย React elements ธรรมดา (ไม่ผ่าน `dangerouslySetInnerHTML`) — ปลอดภัยเท่าเดิมเพราะเนื้อหาแต่ละ
ช่องยังผ่านการ escape อัตโนมัติของ React เหมือนข้อความทั่วไป

ตรวจบล็อกโค้ด (` ``` `) ก่อนเสมอ แล้วค่อยหาตารางเฉพาะในส่วนที่เป็นข้อความล้วน — ป้องกันไม่ให้
เครื่องหมาย `|` ในโค้ดตัวอย่าง (เช่น regex หรือ SQL) ถูกเข้าใจผิดว่าเป็นตาราง

**`TableSystemPrompt`** (ผูกกับ section `Claude` ใน appsettings เช่นเดียวกับ `ChartSystemPrompt`/
`ReportSystemPrompt`) สั่งให้ AI ใส่คำสรุปหรือคำแนะนำสั้น ๆ ต่อท้ายตารางเสมอ ไม่ใช่ส่งตารางดิบ
มาเฉย ๆ — และบอกชัดว่าตัวตารางเองไม่นับรวมในกฎ "ตอบไม่เกิน 6 บรรทัด" ของ Chat mode ปกติ

## 9. ความปลอดภัยที่ใส่ไว้

- **รหัสผ่าน** — PBKDF2-SHA512 210,000 รอบ, salt สุ่ม 16 ไบต์ต่อคน, เทียบแบบ constant-time
- **ล็อกบัญชี** — กรอกผิด 5 ครั้งล็อก 15 นาที (ปรับได้ที่ `Security` ใน appsettings)
- **ไม่เปิดเผยว่ามี username นี้อยู่จริง** — ไม่พบผู้ใช้และรหัสผ่านผิดตอบข้อความเดียวกัน
- **Refresh token** — เก็บเฉพาะ SHA-256, ใช้ครั้งเดียว (rotate), ถูก revoke เมื่อ logout /
  เปลี่ยนรหัสผ่าน / Admin ตั้งรหัสผ่านใหม่ / บัญชีถูกปิดใช้งาน
- **กันล็อกตัวเองออกจากระบบ** — Admin ถอนบทบาท Admin หรือปิดใช้งานบัญชีของตัวเองไม่ได้
- **Audit trail แยกจากข้อมูลผู้ใช้** — ลบผู้ใช้แล้ว audit log ยังอยู่ครบพร้อมชื่อ
- **การเปิดค้น log ถูกบันทึก** — `CHAT_LOG_SEARCHED` เก็บเงื่อนไขที่ใช้ค้นและจำนวนที่พบ
  (บันทึกตอนค้นครั้งแรก ไม่บันทึกซ้ำตอนเปลี่ยนหน้า), export บันทึกทุกครั้ง
- **CSV injection** — ค่าที่ขึ้นต้นด้วย `=` `+` `-` `@` ถูกใส่ `'` นำหน้าก่อน export
- **error ไม่รั่วรายละเอียดระบบ** — exception ที่ไม่คาดคิดตอบข้อความกลาง ส่วนรายละเอียดจริงลง log ฝั่งเซิร์ฟเวอร์

### ต้องทำก่อนขึ้น production

1. เปลี่ยน `Jwt:SigningKey` เป็นค่าสุ่มยาว ≥ 32 ตัวอักษร และเก็บนอกไฟล์ (env var / user-secrets / Key Vault)
2. เปลี่ยนรหัสผ่านผู้ใช้ทดสอบทั้ง 3 คน หรือลบออกจาก `SeedUsers`
3. เลิกใช้บัญชี `sa` — สร้าง SQL login เฉพาะแอปที่มีสิทธิ์แค่ `MGT_AI_Authen`
4. เปิด HTTPS และระบุ `Cors:AllowedOrigins` ให้ชัด (ค่าว่างจะเปิดกว้างทุก origin)
5. พิจารณาย้าย token จาก `localStorage` ไปเป็น httpOnly cookie ถ้าต้องการลดความเสี่ยง XSS
6. วางแผน retention ของ `ChatMessages` / `AuditLogs` ตามนโยบายบริษัทและ PDPA
7. ตรวจราคาใน `ModelPricing` กับราคาประกาศล่าสุดของ **Anthropic, Google และ OpenAI** และตั้งอัตราแลกเปลี่ยน
   ตามที่ฝ่ายบัญชีใช้ ก่อนนำยอดค่าใช้จ่ายไปคิดเงินหรือ charge back เข้าแผนก
   — ดูข้อจำกัดสามข้อของราคา Gemini ในข้อ 6.18 (ราคาสองขั้นที่ 200k token,
   ราคาโปรโมชันที่หมดอายุ 31 ธ.ค. 2026, และโมเดล preview)
9. ถ้าใช้ทะเบียนแหล่งข้อมูล (ข้อ 6.22) และขยายเป็นมากกว่าหนึ่งเครื่อง — ย้าย Data Protection
   key ring จากไฟล์บนเครื่อง (`App_Data/keys`) ไปเป็น network path หรือ Azure Key Vault
   ก่อน ไม่งั้นความลับที่เครื่องหนึ่งเข้ารหัสไว้ อีกเครื่องจะถอดไม่ได้
8. **ตัดสินใจเรื่องไฟล์แนบ:** สำรองข้อมูลโฟลเดอร์ `Uploads:RootPath` ให้ครบเหมือนฐานข้อมูล
   (ไฟล์ไม่ได้อยู่ใน DB), จำกัดสิทธิ์เข้าถึงโฟลเดอร์นั้นในระดับ OS,
   ตั้ง retention ของไฟล์ให้สอดคล้องกับ PDPA, และพิจารณาว่าจะยอมให้ส่ง PDF/รูปภาพต่อไปหรือไม่
   เพราะเนื้อหาข้างในไม่ถูกคัดกรอง (ดูข้อ 6.2)

## 10. หมายเหตุด้านเทคนิค

- **โมเดล** ตั้งไว้ `claude-sonnet-5` (ปรับที่ `Claude.Model`) — เลือกไว้เป็นค่าตั้งต้นเพราะ
  ถูกกว่า Opus ประมาณ 2.5 เท่าที่คุณภาพเพียงพอกับคำถามงานประจำ ผู้ใช้ยังเลือก Opus
  รายข้อความได้จาก dropdown เมื่อจำเป็น (ดูข้อ 6.15) — ทั้ง Sonnet 5 และ Opus 5
  เปิดการคิด (thinking) โดยปริยาย จึงไม่ต้องส่งพารามิเตอร์ `thinking` เอง
- **`Claude.Effort`** (`low`/`medium`/`high`/`max`, เว้นว่าง = ใช้ค่าตั้งต้นของโมเดลคือ `high`)
  ตั้งไว้ `medium` — ดูผลการวัดในข้อ 11 ก่อนปรับ เพราะค่านี้มีผลต่อ **ความเร็วน้อยกว่าที่คาด**
- **`Claude.SystemPrompt`** รองรับ placeholder `{FullName}` `{Username}` `{Department}` `{UserRole}` `{Today}`
  ระบบเติมตัวตนของผู้ถามลงไปทุกครั้ง — AI จึงตอบได้ตรงบริบทแผนก และชัดว่าบทสนทนาผูกกับพนักงานที่ล็อกอินอยู่
- **บริบทบทสนทนา** ส่งย้อนหลัง 20 ข้อความ (`Claude.HistoryTurns`) โดย**ข้าม**ข้อความที่ถูก policy ระงับ
  (เพราะไม่เคยถูกส่งให้ AI) และตัดข้อความ assistant ที่ค้างหัวแถวออก เพราะ API ต้องเริ่มด้วย role `user`
- **การเรียก AI เป็นแบบ non-streaming** (`MaxTokens` 16,000) — คำตอบมาครบก้อนเดียว
  ทำให้บันทึก log ครบทั้งข้อความ, จำนวน token และ latency ได้ในคราวเดียว
  **ข้อเสียที่วัดได้จริง: ผู้ใช้เห็นแค่จุดสามจุดนาน 16–30 วินาที** (ดูข้อ 11)
  ถ้าต้องการให้คำตอบไหลทีละตัวอักษร ต้องเพิ่ม endpoint SSE แยกและบันทึก log ตอน stream จบ
- **`Claude.SystemPrompt` มีข้อ "ความยาวคำตอบ" ที่คุมเวลารอเป็นหลัก** — จำกัดคำตอบไว้ ~6 บรรทัด
  แล้วให้ AI ถามกลับว่าจะขยายส่วนไหน ถ้าอยากได้คำตอบละเอียดกว่านี้ให้ผ่อนข้อนั้นลง
  แต่ต้องยอมรับว่าเวลารอจะเพิ่มขึ้นตามความยาวคำตอบ
- **ข้อความของผู้ใช้ถูกบันทึกก่อนเรียก AI** — ถ้าเรียก AI ไม่สำเร็จ คำถามยังอยู่ใน log
  พร้อม audit `CHAT_FAILED` (ตรวจสอบได้ว่าพนักงานถามอะไรไปแล้วบ้าง แม้ระบบตอบไม่ได้)
- **หน้าเว็บแสดงวันที่เป็น ค.ศ.** (ไม่ใช่ พ.ศ.) เพื่อให้ตรงกับตัวกรอง `<input type="date">`,
  ค่าที่เก็บใน SQL Server และไฟล์ CSV — ผู้ตรวจสอบเทียบข้อมูลข้ามระบบได้ตรง

ชุดหลักครอบคลุม:

- ล็อกอิน/รหัสผ่านผิด/ล็อกบัญชีเมื่อผิด 5 ครั้ง, refresh (รวมทั้งใช้ token ซ้ำต้องไม่ได้), logout,
  เปลี่ยนรหัสผ่าน (รหัสเดิมต้องใช้ไม่ได้)
- สิทธิ์ตามบทบาททั้ง 3 (User เข้าหน้า log ไม่ได้ → 403, Auditor แก้ policy/ผู้ใช้ไม่ได้ → 403)
- จัดหมวดคำถามครบทั้ง 8 ประเภทจากประโยคภาษาไทย
- คัดกรอง Block/Warn/Audit และข้อความปกติที่ต้องผ่าน
- ค้น log ทุกเงื่อนไข — คำค้นภาษาไทย, ตามคน/แผนก/ประเภท/ธง/ช่วงวันที่, เงื่อนไขผสม, เรียงลำดับ, แบ่งหน้า
- สรุปสถิติ, export CSV (ตรวจถึงระดับ byte ว่ามี BOM `EF BB BF`)
- ต่อบทสนทนาใน session เดิม, ซ่อน session แล้ว log ต้องยังค้นเจอ
- CRUD เงื่อนไขคัดกรอง (รวมการปฏิเสธ regex ที่ผิดรูปแบบ) และ CRUD ผู้ใช้ (กันชื่อซ้ำ, กันรหัสผ่านอ่อน)

ชุด **Keyword หลายคำ** ตรวจว่าเงื่อนไขที่คั่นจุลภาคจับได้ทุกคำ (ทั้งไทยและอังกฤษ, ไม่แยกตัวพิมพ์),
รูลเดิมที่มีคำเดียวและรูล Regex ไม่กระทบ, และข้อความที่ไม่มีคำในรายการต้องผ่าน

ชุด **token/ค่าใช้จ่าย** ตรวจถึงระดับตัวเลข:

- ยอด USD ที่ระบบคำนวณตรงกับที่คำนวณมือทุกหลัก (เทียบ `(token/1M) × ราคา` แยกทุกประเภท)
- ยอดบาท = USD × เรตที่บันทึกไว้

**ปัญหาที่เจอระหว่างทดสอบและแก้แล้ว 4 จุด:**

1. **ConfigurationBinder ของ .NET "ต่อท้าย" array ไม่ได้แทนที่** — `AllowedExtensions` ที่มี

3. **400 จาก Anthropic ถูกตอบเป็น 502 "เรียกใช้ AI ไม่สำเร็จ"** ทั้งที่สาเหตุคือรูปที่โมเดล

4. **เครดิต Anthropic หมดถูกตอบว่า "ข้อมูลที่ส่งไปไม่ถูกต้อง"** ทำให้ผู้ดูแลไล่หาสาเหตุผิดทาง

   `ClaudeBillingException` → 503 code `CLAUDE_BILLING` พร้อมบอกชัดว่าไม่ใช่ปัญหาที่ไฟล์ของผู้ใช้

ชุด **การทำกราฟ** (34 เคส) ตรวจสองชั้น — spec ที่โมเดลส่งมาใช้ได้จริง และตัวเลขในกราฟ

- **ความลับไม่เคยเป็น plain text ในฐานข้อมูล** ตรวจโดยอ่านค่าตรงจาก `DataSources.EncryptedSecret`

- แก้ไขแหล่งข้อมูลแล้วเว้นช่อง secret ว่างไว้ **คงค่าเดิม** ไม่ใช่ล้างทิ้ง (ยืนยันด้วยการเทียบ
  ค่าที่เข้ารหัสก่อน-หลังตรงจากฐานข้อมูล)
- config ที่ขาดฟิลด์บังคับ, `authType` ที่ไม่รู้จัก และชื่อซ้ำ ถูกปฏิเสธ
- **ทดสอบเชื่อมต่อได้จริง** — โฟลเดอร์ที่มี/ไม่มีจริงบนเครื่อง, ยิง HTTP ไปที่ API ที่มีจริง/ไม่มีจริง,
  และ **Data Lake (Fabric/Power BI) ที่ config ครบแต่ credential ปลอม ถูก Entra ID ปฏิเสธจริง**
  (ไม่ใช่ stub ตอบ "ยังไม่มี connector" อีกต่อไป) พร้อม config ที่ขาดฟิลด์บังคับถูกปฏิเสธ 400
- **สองเคสตัวอย่างที่ผู้ใช้ระบุไว้โดยตรง**: ให้สิทธิ์ Custom scope จำกัด endpoint (เคส CFO/SAP)
  และให้สิทธิ์ Own department ที่ผูกกับ `Users.Department` อัตโนมัติโดยไม่ต้องพิมพ์ชื่อแผนกซ้ำ
  (เคส Sales Manager) — และ **ปฏิเสธ** Own department ถ้าพนักงานยังไม่มีแผนก แทนที่จะกลายเป็น
  Full สิทธิ์อย่างเงียบ ๆ
- ให้สิทธิ์ซ้ำแล้วเหลือแถว active แค่แถวเดียว, เพิกถอนแล้วแถวยังอยู่ (isActive=false ไม่ใช่ถูกลบ),
  เพิกถอนซ้ำถูกปฏิเสธ, ลบแหล่งข้อมูลที่มีประวัติ grant ไม่ได้
- audit log บันทึกครบทั้งห้าการกระทำ (created/updated/tested/granted/revoked)

ทดสอบ frontend บนเบราว์เซอร์: ล็อกอินทั้ง 3 บทบาท, ส่งข้อความที่ถูกระงับแล้วเห็นการแจ้งเตือน,
ถามคำถามจริงแล้วได้คำตอบจาก Claude, หน้าค้น log พร้อมสถิติและปุ่มเงื่อนไขที่ใช้บ่อย, หน้า audit log,
หน้าเงื่อนไขคัดกรอง (รวมช่องทดลองยิงข้อความ), หน้าจัดการผู้ใช้, การซ่อนเมนูตามบทบาท
และ layout แบบจอแคบ

บั๊ก UI ที่เจอและแก้แล้ว 4 จุด:

1. กราฟแท่งไม่แสดง — `.bar-track` เป็น `<span>` ซึ่งเป็น inline element จึงไม่รับค่า `height`
2. วันที่แสดงเป็น พ.ศ. (`th-TH` ใช้ปฏิทินพุทธเป็นค่าตั้งต้น) ไม่ตรงกับตัวกรอง `<input type="date">`
   และค่าใน SQL — เปลี่ยนเป็น `th-TH-u-ca-gregory`
3. หลังล็อกอิน ระบบพากลับไปหน้าที่บทบาทนั้นเปิดไม่ได้ — เพิ่ม `lib/routes.js` ตรวจสิทธิ์ปลายทางก่อน

   เลื่อนแค่แนวนอน — แก้ให้เป็น scroll container จริง (`overflow: auto` + `max-height: 70vh`)

คำถาม `"ทำไมต้องมี Safety Data Sheet"` ยิงซ้ำหลายรอบ:
